# 開発ワークフロー仕様

## 基本方針

実装タスクでは、実装方針、テスト設計、レビュー、最終検証に責任を持つ。

## Agent Field Guide

エージェントが実作業中に得た、次のエージェントの試行錯誤を減らす非自明で再利用可能な知見は、`agent-field-guide/`へ記録する。

- 作業開始時は`agent-field-guide/INDEX.md`を確認し、現在の作業に関係するエントリーだけを読む。
- 作業中に失敗の原因、成功した手順、再発を早期に見分ける兆候が分かった場合は、既存エントリーを検索し、完了前に追加または更新する。
- Field Guideの記録に専用タスクを作成する必要はない。タスクに紐づかない調査、環境差分、Cursor CLIなどのツール委任で得た知見も対象とする。
- 関連タスク、commit、コードパス、テストパス、確認日は任意とし、記録の前提条件にしない。
- Field Guideは製品仕様、必須ルール、タスク管理の代替にしない。Field Guideの知見が必須要件や恒久的な開発ルールになった場合は、`specs/`、`AGENTS.md`、テストへ反映する。
- 記載基準と更新方法は`agent-field-guide/README.md`、エントリー形式は`agent-field-guide/ENTRY_TEMPLATE.md`に従う。

## タスク作成時の難易度評価

新しい`tasks/open/*.md`には、背景や目的の後、遅くとも対象範囲より前に`## 難易度`セクションを設ける。次の形式で、判定結果だけでなく根拠も残す。

```markdown
## 難易度

- 判定: 中
- 理由: 複数コンポーネントの状態連携を変更するが、既存の境界内に収まり、仕様上の未知要素は少ないため。
```

判定基準は以下とする。

- `高`: 大規模な設計変更、広い影響範囲、未知要素の多い調査、複数の状態や境界が交差する処理、回帰・安全性リスクの高い変更など、複雑な判断が必要なタスク。
- `中`: 複数ファイルやコンポーネントにまたがり、一定の設計判断や回帰確認が必要だが、既存の境界と実装パターンを利用できるタスク。
- `低`: 変更箇所と期待結果が明確で、局所的な実装、文言変更、定型的なテスト追加などのタスク。

難易度は見込み作業時間や変更行数だけでは決めず、設計判断の複雑さ、影響範囲、未知要素、回帰・安全性リスク、テスト難度を総合して決める。実装開始時に再確認し、調査によって前提や対象範囲が変わった場合は、実装前にタスク本文の判定・理由を更新する。既存の`tasks/done/`へ遡って追記する必要はない。

## タスク進行手順

1. 対象タスクを読み、難易度判定が現在の対象範囲と合っているか確認する。
2. 関連仕様と既存コードを確認し、実装方針を決める。
3. 「テスト方針・設計基準」に従い検証方法を先に決め、挙動変更・不具合修正では失敗するテストを優先して用意する。
4. 実装し、変更をレビューする。
5. 変更範囲に応じたテスト・型チェック・手動確認を実行し、結果と未確認事項を報告する。
6. 完了したタスクを`tasks/open/`から`tasks/done/`へ移動する。
7. 関連変更をgit commitする。

## テスト方針・設計基準

この節をテストの追加・修正・削除と実行範囲の判断基準の正本とする。製品として保証する動作は`specs/novel-editor-mvp.md`の「テスト」と関連機能仕様を参照する。テスト数や実装行数への追随を目的にせず、検出できる不具合と保守コストで判断する。

### 1. 守る振る舞いを固定する

- 外部契約、利用者から観測できる操作結果、安全上の不変条件を優先して検証する。
- クラス名、DOM構造、CSSの記述、説明文の完全一致、内部関数の呼び出し順序は、固定自体が要件である場合だけ検証し、理由をテスト名やコメントで示す。安全性に必要な設定や呼び出し禁止の検証は維持する。
- UIはrole、label、accessible nameと操作後の状態を基本とする。外観の保証にはブラウザ上の表示・寸法や画面確認を使い、CSS文字列の一致を表示結果の保証として扱わない。寸法を検証する場合はviewportなどの前提と許容範囲を定める。
- 振る舞いを変えないリファクタリングや文言の推敲でテスト修正が必要になったら、固定している内容が要件かを再確認する。テスト削除時は、その保証が不要になった理由または移行先を示す。

### 2. ブラウザテストの保証範囲を明示する

- APIをモックするUI結合テストと、実API・一時ワークスペースを通すE2Eをテスト名、describe、またはfixtureの説明で区別する。
- APIモックを使った保存・再読み込みの確認は、UIの連携を保証する。実サーバーの保存処理や永続化を保証したとは扱わない。
- 原稿の「開く→編集→保存→再取得」、AI編集の「適用→取り消し→原文復元」など、重要な利用フローは少数の実API・実保存経路のE2Eで保証する。LLMやネイティブ選択UIなどの外部境界は置き換えてよいが、何を置き換えたかを明示する。
- 実LLMの応答品質と配布アプリの実機動作は別の評価として扱い、モックを使った自動テストの成功で代用しない。

### 3. 正常系fixtureを本番の契約に合わせる

- 正常系fixtureとモックは型注釈や`satisfies`で本番の型への適合を確認する。`as never`や`as unknown as`による契約検証の回避は原則行わない。
- 不正入力のテストで必要な型回避は入力境界に限定する。外部SDKの巨大な型など、部分的な代替が必要な場合は理由を明示し、型回避を限定したhelperへ閉じ込める。
- API応答モックは共通の応答型やschemaに適合させる。型だけでは確認できないシリアライズやdecoderとの整合は実APIの契約テストで確認する。
- fixtureの共通化は安定した契約・生成処理に限定し、シナリオ固有の入力と期待結果はそのテストから読める形を保つ。

### 4. 保証を担当する層を決める

- 分岐、境界値、不正入力は、その責務を持つ最小の層で詳しく検証する。上位層は接続、変換、代表的な利用フローを検証する。
- 例えばパス拒否の組み合わせはサービス、HTTP応答への変換はAPI、エラー表示はUIで確認する。各層で同じ組み合わせを繰り返す場合は、その層で別に検出できる不具合を説明できること。
- 異なる入口から安全境界を迂回できないことの確認など、固有のリスクがある重複は維持する。
- ファイル操作の安全性は、一時ディレクトリ内の実ファイルを使って検証する。パス検証や保存処理そのものをモックして安全性を保証したとは扱わない。

### 5. リスクに応じた検証を先に決める

実装前にメインエージェントが検出すべき失敗、保証する層、検証方法を決める。

- 挙動変更・不具合修正では、変更前に意図した理由で失敗するテストを優先して用意する。失敗が環境不備や無関係なエラーによるものではないことを確認する。
- 挙動不変の内部整理では、既存テストと型チェックを先行する検証として使える。軽微な文書・外観変更では、文書の整合確認や画面確認を選べる。操作、フォーカス、アクセシビリティなどの挙動を変える場合は、外観変更だけとは扱わない。
- 新規テストを追加しない場合、またはテストを先に書けない場合は、理由と代替の検証方法をタスク本文または作業報告に明示する。初期構築で前提がない場合も、最小のスモークテストまたは検証手順を先に定義する。
- 原稿の消失・上書き、権限、秘密情報に関わる変更は重点的に検証する。正常系に加えて、該当する失敗時の非変更、競合、再試行の二重適用防止、取り消し・復元、秘密情報の非露出を確認する。

### 6. 実行した検証と保証範囲を報告する

変更に該当する行の検証を組み合わせる。開発中は対象テストを使い、コード変更の完了時には全体回帰を確認する。

| 変更範囲 | 必須の検証 |
| --- | --- |
| TypeScript/TSXの実装・テスト・型契約 | `bun run test`と`bun run typecheck` |
| UI操作・画面間連携・ブラウザ固有動作 | 関連するPlaywrightを`bun run test:e2e -- <対象ファイル>`で実行。共通の画面基盤変更ではPlaywright全体を実行 |
| desktop起動・通信・ネイティブ境界 | `bun run test:desktop`。OSや配布形態に依存する部分は対象環境でも確認 |
| LLM・外部CLIとの契約や品質に影響する変更 | 関連する契約テストに加え、変更した境界のlive smokeや品質評価。必要な対象version・環境を明記 |
| 文書のみ・軽微な外観のみ | 差分と仕様の整合確認、関連する既存テストがあればその実行。外観は画面確認を行う |

`bun run test`はVitestの全体実行であり、Playwright、型チェック、desktop検証を含まない。`bun test`はこのプロジェクトのVitest設定を通らないため使わない。

Vitestは専用の`vitest.config.ts`でNodeとDOMのプロジェクトを分ける。DOM不要のテストにはjsdomやDOM用setupを読み込まず、アプリ起動用Viteプラグインも使わない。TSXテストと`domTests`に列挙したブラウザAPI依存のTSテストをDOM側で実行する。テスト対象の呼び出し先がブラウザAPIに依存する場合もDOM側に含める。開発中は`bun run test --project node`、`bun run test --project dom`、または対象ファイル指定で絞り込めるが、完了時の全体実行は省略しない。

完了報告では実行したコマンド・手動確認と結果、未実行の検証と理由を明記する。環境や認証などの制約で必要な確認ができない場合は未確認として残し、モックや別OSでの成功をその保証に置き換えない。CIでも変更範囲に応じた検証を実行し、CIで実行されない項目はローカルまたは対象環境で補う。

### テストの配置

Vitestのテストは対象実装の近くに配置する。Reactコンポーネントのテストも対象コンポーネントの近くに配置する。Playwrightのテストは`e2e/`配下に配置する。

共通テストヘルパーは必要になった場合だけ`src/shared/test/`に置く。fixtureはfeature固有なら対象feature配下、横断的なら`tests/fixtures/`に置く。

## レビュー観点

メインエージェントは以下を優先して確認する。

- 仕様を満たしているか。
- テストが意図した失敗を検出できるか。固定対象、保証する層、fixtureの契約、モックの範囲が「テスト方針・設計基準」に沿っているか。
- ワークスペース外アクセスなどの安全性を壊していないか。
- AI編集が承認制を守っているか。
- Vercel AI SDKの型と設計に沿っているか。
- vertical slice構成を崩していないか。
- 不要な抽象化や広すぎる変更がないか。

## 完了条件

タスクは以下を満たしたときに完了とする。

- 対象タスクの完了条件を満たしている。
- 変更範囲に応じたテスト・型チェック・手動確認が成功し、実行結果と未確認事項が報告されている。
- レビュー指摘が解消されている。
- 変更内容が仕様書と矛盾していない。
- 完了タスクが`tasks/done/`へ移動されている。
- 関連変更がgit commitされている。
