# アイディアメモ

このファイルは、まだ実装タスク化しないアイディアを残す場所です。実装に入る場合は、改めて`tasks/open/`へ連番タスクを作成します。

## 文書ワークスペース向けコンテキスト

### タイトルインデックス

- Markdownなら先頭の`#`見出し、プレーンテキストなら先頭行を拾い、ファイルパスと対応付けた軽量インデックスを作る。
- 全文要約よりstaleリスクを抑えつつ、エージェントが「どこに何がありそうか」を把握しやすくする。
- 本文を丸ごとキャッシュせず、必要な本文は`Read`や`Search`で取得する方針を維持する。

### inbox / drafts / todo / wip 領域の検出

- `inbox/`、`drafts/`、`todo/`、`wip/`、`open/`など未整理・作業中らしいディレクトリやファイル名を検出する。
- コーディング以外の文書作業では、未処理メモ、下書き、作業中テキストの所在が初動判断に効く。
- ディレクトリ名の推定だけで対象確定せず、必要に応じてユーザー確認やツール確認を挟む。

## ユーザー追加Skillsとplugin拡張

まだ仕様検討段階のメモ。現行の`AgentSkill`は、信頼済みローカル定義からsystem promptへ追加する指示であり、任意scriptを実行する仕組みではない。ユーザーが後から追加できる仕組みを検討するときは、指示、定型workflow、実行可能コードを同じ「Skill」として混ぜない。

### 拡張種別の分離

- 宣言的Skill: MarkdownまたはJSONで記述する手順、専門知識、文体ガイド。system promptへの追加だけを行い、tool権限や任意コード実行能力を持たない。
- Workflow: アプリが既に許可しているtoolを定型的な順序で利用する宣言。直接ファイルシステム、shell、networkへアクセスしない。
- Executable Tool Plugin: 新しいAI toolや外部サービス連携を実装する信頼済みコード。宣言的Skillとは別種のpluginとして扱い、明示的なinstall、enable、権限確認を必要とする。
- LLM Provider Plugin: provider/model生成と接続設定を追加する拡張。Agent Tool Pluginとは分け、APIキーとSecret Storeの扱いを専用境界に閉じ込める。

最初のユーザー追加対応では、任意コードを実行しない宣言的Skillだけを対象にする案が安全。WorkflowとExecutable Tool Pluginは、manifest、権限、更新、互換性、sandbox方針を決めてから段階的に扱う。

### 配置と読み込み

- ユーザー追加拡張はワークスペース内ではなく、OSのアプリデータディレクトリ配下の専用領域へ保存する案を優先する。
- ワークスペース内の`.skills/`、`AGENTS.md`、会話履歴、チャット入力から実行可能pluginを自動ロードしない。
- installとenableを分け、存在するだけでは実行対象にしない。
- 起動時または設定変更時にmanifestをZodで検証し、不正な拡張だけを無効化して理由を表示する。
- built-inとユーザー追加のID衝突、複数plugin間のSkill ID/tool名衝突は決定論的に拒否する。
- Skill/tool一覧には`pluginId`、version、sourceなどのprovenanceを保持し、どの拡張が提供したか確認できるようにする。

### manifest案

```ts
type PluginManifest = {
  id: string;
  name: string;
  version: string;
  apiVersion: string;
  kind: "agent-skill" | "agent-workflow" | "agent-tool" | "llm-provider";
  entry?: string;
  requestedCapabilities?: string[];
};
```

- `apiVersion`でアプリ側plugin APIとの互換性を判定する。
- 宣言的Skillでは`entry`を実行ファイルとして使わず、検証済みのSkill定義ファイルを参照する。
- 実行可能pluginではentry pathをplugin root内へ正規化し、plugin root外への脱出を拒否する。
- manifestやUI表示へAPIキー、認証token、ワークスペース本文を保存しない。

### capabilityと安全性

- capability候補は`workspace:read`、`workspace:search`、`workspace:propose-edit`、`network`、`secrets:<provider>`などに分ける。
- capabilityはpluginの自己申告だけで許可せず、アプリ側の明示grantと一致したものだけを渡す。
- `AgentProfile.activeTools`、ワークスペース境界、AI編集承認制、APIキー秘匿、件数・行数制限はpluginから緩和できない。
- ファイル操作は直接Node.js APIを渡さず、`WorkspaceFileStore`、`WorkspaceSearchStore`、編集proposal serviceなどの制限済みservice経由にする。
- 宣言的Skillの`requiredTools`は権限追加に使わず、不足toolがある場合の利用不可理由または警告にだけ使う。
- shell、任意module import、任意network accessを許すpluginはローカルコード実行と同等の危険性があるため、sandboxなしで一般ユーザー向けに有効化しない。

### 管理UI案

- install済みplugin/Skillの一覧、source、version、状態、要求権限を表示する。
- enable/disable、削除、互換性エラー確認、更新確認を提供する。
- Skillが有効化されたとき、チャットのtool activityなどからSkill名と提供元を確認できるようにする。
- 実行可能pluginの有効化時は、読み取り、編集提案、network、secret利用などの影響を明示する。

### 未決事項

- 宣言的Skillの配布形式を単一Markdown、directory bundle、zipのどれにするか。
- plugin署名、配布元の信頼、更新manifest、rollbackをどこまで初期対応するか。
- JavaScript/TypeScript pluginを同一process、worker、別processのどこで実行するか。
- networkやsecret accessをpluginごとにどの粒度で許可するか。
- pluginが追加する設定画面やrouteを動的ルーティングとどう統合するか。
- desktop版とWeb開発版で同じplugin形式をサポートするか。

## 他サービスからのインポート支援

まだ仕様検討段階のメモ。テスターから、他サービスからのインポートができるとよいのではないかというアイディアがあった。

インポート元サービスの幅が広く、各サービス専用の決定論的なパーサーを最初から揃えるのは重い。一方で、このアプリはLLM利用を前提にしているため、LLMにインポート元のディレクトリ構成やテキストファイルの内容を見せ、標準ワークスペース構成への変換方針を提案させる方向は有望。

### 基本アイディア

- 入力はローカルディレクトリとテキストファイルを前提にする。
- アプリ側でファイル一覧、相対パス、サイズ、先頭数行などを収集する。
- LLMには任意スクリプトではなく、インポート計画のJSONを生成させる。
- 実際のファイル作成、コピー、本文変換、上書き判定はアプリ側の決定論的な処理で行う。
- 実行前に、作成予定の章、設定資料、メモ、衝突ファイルをプレビューする。
- 変換後は通常のワークスペース内ファイルとして扱い、専用の不可視データストアを作らない。

### LLMに任せたい判断

- どのファイルが章本文、設定資料、プロット、メモに相当するか。
- 章番号や章順を、ファイル名、ディレクトリ名、本文見出しから推定する。
- サービス由来のヘッダー、フッター、目次、不要な区切り行を除去すべきか提案する。
- 既存の標準構成（`小説/第001章/本文.txt`、`設定/登場人物.md`など）への配置案を作る。

### 安全面の方針

- LLMが生成したスクリプトをそのまま実行する方式は避ける。
- LLM出力はZodで検証できるJSONのインポート計画に限定する。
- パスはワークスペースルート基準で正規化・検証し、ワークスペース外への書き込みを拒否する。
- バイナリに見えるファイルは対象外にする。
- `.`から始まるセグメントを含むパスは既存ルールに合わせて編集不可にする。
- 既存ファイルの上書きは、少なくとも明示的なプレビューと承認を必要にする。
- 失敗時に再実行しやすいよう、インポート計画と適用結果をユーザーに見える形で残すことを検討する。

### 未決事項

- 既存ワークスペースへ追加インポートするのか、新規ワークスペース作成フローに統合するのか。
- インポート計画の保存場所を会話履歴だけにするか、ワークスペース内の通常ファイルとして残すか。
- 対象サービスごとのプリセットを持つか、最初は汎用インポートだけにするか。
- 本文の記法変換（ルビ、傍点、改ページ、区切り線）をどこまで扱うか。
- 大量ファイルや長大本文を扱う場合、LLMへ渡すサンプル量と分割方法をどうするか。

## 置換機能

### ユーザー向けの現在ファイル内置換

- CodeMirrorの通常編集機能として、現在開いているファイル内の検索・置換を追加する。
- `Replace next`と`Replace all`を用意し、置換後は通常の手編集と同じく未保存状態にする。
- まずは現在ファイル内だけを対象にし、ワークスペース全体置換は別アイディアまたは別タスクとして扱う。

### エージェント向けの置換編集案

- エージェントにも置換能力は持たせるが、直接ファイルを書き換えるツールにはしない。
- `proposeTextReplacement`のような、置換内容からAI編集案を作るツールとして扱う。
- Applyは既存のAI編集案フローと同じくユーザー承認制にし、1件ずつ適用する。
- 未保存状態のファイルにはAI編集Apply不可という既存制約を維持する。
- 複数ファイル置換は、件数プレビューとファイル別diffを前提にした後続検討にする。

## なろう・カクヨムのルビ／傍点入力支援

まだ仕様検討段階のメモ。実装に入る場合は、改めて`tasks/open/`へ連番タスクを作成し、エディター入力支援、プレビュー、リーダーモード表示、AI編集案での扱いを分けて検討する。

### 小説家になろう

#### ルビ記法

小説家になろうでは、以下の形式でルビを指定できる。

```text
｜親文字《ルビ》
```

例:

```text
｜山田太郎《やまだたろう》
```

半角の縦線も使用できる。

```text
|山田太郎《やまだたろう》
```

#### 縦線を省略したルビ

親文字が漢字の場合、縦線を省略できる。

```text
親文字《ルビ》
```

例:

```text
山田太郎《やまだたろう》
```

#### 丸括弧によるルビ

小説家になろうでは、親文字が漢字で、ルビがひらがな・カタカナの場合、丸括弧でもルビとして扱われる。

```text
親文字(ルビ)
親文字（ルビ）
```

例:

```text
山田太郎(やまだたろう)
山田太郎（やまだたろう）
```

#### 丸括弧ルビを回避する記法

丸括弧をルビとして扱わせたくない場合、丸括弧の直前に縦線を入れる。

```text
親文字｜(ルビ)
親文字｜（ルビ）
```

例:

```text
山田太郎｜(やまだたろう)
山田太郎｜（やまだたろう）
```

#### 傍点記法

小説家になろうには、カクヨムの`《《文字》》`のような傍点記法はない。

傍点を表現したい場合は、投稿サイト側のルビ記法などを使って疑似的に表現する必要がある。

### カクヨム

#### ルビ記法

カクヨムでは、以下の形式でルビを指定できる。

```text
親文字《ルビ》
```

例:

```text
彼女《ヒロイン》
```

#### 縦線を使ったルビ範囲指定

親文字に漢字以外を含めたい場合や、ルビを振る範囲を明示したい場合は、縦線を使う。

```text
｜親文字《ルビ》
```

例:

```text
｜紅蓮の炎《ヘルフレイム》
｜etc《えとせとら》
```

半角の縦線も使用できる。

```text
|親文字《ルビ》
```

例:

```text
|etc《えとせとら》
```

#### 文字数制限

カクヨムでは、ルビ記法に以下の文字数制限がある。

```text
親文字: 最大20文字
ルビ: 最大50文字
```

#### 傍点記法

カクヨムでは、以下の形式で傍点を指定できる。

```text
《《傍点を付けたい文字》》
```

例:

```text
これは《《重要》》です。
```

### 共通して使いやすい記法

なろう・カクヨムの両方で使いやすいルビ記法は以下。

```text
｜親文字《ルビ》
|親文字《ルビ》
漢字列《ルビ》
```

例:

```text
｜山田太郎《やまだたろう》
|山田太郎《やまだたろう》
山田太郎《やまだたろう》
```

カクヨムの傍点記法は以下。

```text
《《傍点》》
```

例:

```text
これは《《重要》》です。
```

ただし、この傍点記法はカクヨム向けであり、小説家になろうの標準的な傍点記法ではない。
