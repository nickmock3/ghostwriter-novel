# Ghostwriter MVP仕様

## 概要

ユーザーが選択したローカルワークスペース内の小説原稿、設定資料、執筆メモなどのテキストファイルを対象に、閲覧・編集・検索・AIによる執筆支援を行うアプリケーションを作成する。

アプリケーションはローカル小説執筆ワークスペース向けのAI付き3ペインエディターを中核として動作する。会話主体のチャットモード、3ペインのエディットモード、読書専用のリーダーモードの3モードを持ち、左端サイドバーから切り替えられる。詳細は「モード構成」に従う。開発時のWeb実行に加え、macOS Apple SiliconとWindows x64向けにはTauri v2を使ったデスクトップアプリとして配布する。

実装タスクの進め方は`specs/development-workflow.md`に従う。

エディットモードの画面構成:

- 左端サイドバー: 画面切り替えナビゲーション
- 左ペイン: ファイルツリー
- 中央ペイン: CodeMirrorテキストエディター
- 右ペイン: 現在の原稿へ単発のAI処理を実行するAIアシスト

ワークスペース内のファイルは、バイナリまたはテキストとして安全に扱えないと判断されない限り、拡張子に関係なくテキストとして扱う。

## 目的

- Web UIからローカルワークスペースを選択できるようにする。
- 選択したワークスペースの原稿、設定資料、執筆メモをファイルツリーで表示する。
- CodeMirrorで原稿や関連テキストファイルを開き、編集し、保存できるようにする。
- チャットモードからワークスペース内の原稿や資料を調査し、執筆・推敲・整理を進められるようにする。
- エディットモードのAIアシストから、現在の選択範囲または開いているファイルを対象に、推敲、校正、ルビ候補作成などの単発処理を実行できるようにする。
- ワークスペース直下の`AGENTS.md`をエージェントへの追加指示として読み込めるようにする。
- 章ごとの概要、プロット、メモをユーザーに見える通常ファイルとして扱い、AIが現在の章の参考資料として優先参照できるようにする。
- ファイル探索と本文検索は検索ストア境界越しに扱い、ローカル実装では`ripgrep`を使う。
- チャット履歴をJSONで保存する。
- エディットモードでは、AIによるファイル編集を必ずユーザー承認制にする。チャットモードでは自動適用を既定とし、適用済みカードと取り消しで可視性と復元性を保つ。

## MVPで対象外とすること

- 複数ユーザーでの共同編集。
- Ghostwriter独自のユーザー認証。ChatGPT接続の認証はSIWC直接接続の定義に従う。
- リモートワークスペース。
- ベクトルデータベース検索。
- Git連携。
- バイナリファイル編集。
- エディットモードのAIアシストが作成した編集案の、ユーザー承認なしの自動適用。チャットモードは「モード構成」の定義に従い自動適用を既定とする。

## 技術スタック

- ランタイム: Bun
- 言語: TypeScript
- フロントエンド: React + TanStack Start
- エディター: CodeMirror
- スキーマ検証: Zod
- 単体/結合テスト: Vitest
- ブラウザ/e2eテスト: Playwright
- 検索バックエンド: 検索ストア境界越しのローカル`ripgrep`
- AI実行方式: Vercel AI SDK
- AIプロバイダー: Vercel AI SDKの`@ai-sdk/deepseek`、`@ai-sdk/openai`、`@ai-sdk/google`、`@ai-sdk/anthropic`
- デスクトップシェル: Tauri v2

## デスクトップアプリ構成

macOS Apple SiliconとWindows x64向けデスクトップ版は、Tauri v2のWebViewへ静的SPAを読み込み、既存のTypeScriptサーバー機能をローカルsidecarとして起動する。

- UIはTauriが配信する静的SPAとして動作し、SSRを必須にしない。
- 配布targetはmacOSの`aarch64-apple-darwin`とWindowsの`x86_64-pc-windows-msvc`だけとする。macOS IntelとWindows ARM64は対象外とする。
- Vercel AI SDK、AIストリーミング、ファイル操作、検索、会話履歴、テンプレート、LLMシークレット管理は、既存のTypeScript境界を維持したローカルsidecarで実行する。
- Rust/Tauri commandsへの全面移植は初期導入の対象外とする。ネイティブダイアログ、プロセスライフサイクル、アプリデータディレクトリ取得など、Tauriが担当する方が適切な機能だけを段階的に移す。
- sidecarはループバックアドレスだけで待ち受け、起動ごとに生成する認証情報でTauri WebViewからの要求だけを受け付ける。
- Windowsデスクトップ版では、sidecar本体に加え、ripgrep検索などバックグラウンドの子プロセスもコンソール非表示で起動する。
- デスクトップ版の会話履歴とユーザー定義テンプレートは、カレントディレクトリではなくOSのアプリデータディレクトリ配下へ保存する。
- `ripgrep`は利用者の`PATH`に依存せず、対象OS・CPU向けバイナリを配布物へ含める。
- APIキー本文はデスクトップ版でもsidecarまたはネイティブ側だけで扱い、WebView、`localStorage`、会話履歴、ワークスペース内ファイルへ保存しない。
- TauriのcapabilityとCSPは必要最小限にし、任意コマンド実行やワークスペース全体への無制限なフロントエンド権限を与えない。
- 開発時のWeb実行は維持し、クライアントのAPI transport境界でWeb版の同一origin APIとデスクトップ版のsidecar APIを切り替える。
- 初回preview配布（`0.1.0-preview.1`）は未署名artifactをCloudflare R2へ配置し、限定テスター向けに手動ダウンロードで配布する。macOS Gatekeeper警告とWindows SmartScreen警告が出る前提とする。
- preview配布ではTauri auto updaterを含めない。更新はR2上の新しいartifactを手動ダウンロードして置き換える。
- macOSのコード署名・notarizationとStore外Windows code signingはタスク`054`、macOSとStore外WindowsのTauri updaterはタスク`055`で扱う。Microsoft Store版WindowsはStoreの署名と更新配信を利用する。
- Windowsの最初の一般リリースはMicrosoft Store向けMSIXとする。Partner Centerで予約したPackage Identityを使い、Store提出artifactは自前の有料コード署名証明書を前提にせずMicrosoft Storeの署名・配信・更新を利用する。ローカルsideload検証用署名はStore提出artifactと分離し、証明書や秘密鍵をリポジトリへ保存しない。

詳細な影響範囲と採用理由は`specs/tauri-desktop-impact.md`に記載する。

## ワークスペース選択

アプリ起動直後は、アクティブなワークスペースがない状態にする。

UIに「ワークスペースを開く」操作を用意する。Tauriデスクトップ版ではTauriのネイティブディレクトリ選択ダイアログを使う。Web開発版では、macOSはBunサーバー側から`osascript`、WindowsはPowerShellと.NETのフォルダー選択ダイアログを使う既存方式を維持する。Linuxなどネイティブ選択を提供しない環境では、手動パス入力でワークスペースを指定できるようにする。

ネイティブ選択に失敗した場合、または対象OSでネイティブ選択を提供しない場合は、内部コマンド名やspawnエラーをそのまま表示せず、手動パス入力などのフォールバックを提示する。手動入力されたパスはサーバー側のワークスペース検証APIを通過した場合だけアクティブなワークスペースとして採用する。

ワークスペースのルール:

- アクティブなワークスペースルートは絶対パスで保持する。
- すべてのファイル操作はワークスペースルート配下に限定する。
- シンボリックリンク経由でワークスペース外へ抜けられないようにする。
- 直近で開いたワークスペースはアプリのメタデータとして保存してよい。

起動時の前回ワークスペース復元:

- 「最後に開いたワークスペースを復元する」がONで保存済みワークスペースがある場合、サーバー側の検証が完了するまでは復元中として扱う。復元中は初回のワークスペース準備モーダル、ヘッダーの「未選択」、各モードの空状態案内を出さず、ヘッダーとチャット・エディット・リーダーの各モードに「前回のワークスペースを開いています…」という控えめな読み込み表示を出す。復元中もワークスペースを開く操作は利用でき、別のワークスペースを選んだ場合は後から完了した復元結果で上書きしない。
- 復元前の最初の描画（SPAシェル）でも保存済みワークスペースの有無は判断できないため、未選択画面ではなく読み込み表示を出す。画面のコード読み込み中も空白にせず読み込み表示を出す。
- 検証に失敗した場合は、前回の場所を示す復旧用モーダルを出す。保存済みワークスペースがない場合、または復元設定がOFFの場合は、起動直後から未選択状態（エディットでは初回モーダル、チャット・リーダーでは空状態案内）を出す。

### 新規ワークスペーステンプレート

MVPでは、既存のワークスペースを開く操作とは別に、ユーザーが明示的に選んだ場合だけ新規ワークスペース向けの内蔵テンプレートを適用できる。

テンプレートは、サーバー側のアプリ内定義テンプレートと、UIで作成・編集したユーザー定義テンプレートを扱えるようにする。初期状態では、以下を作成するアプリ内定義テンプレートを用意する。

- `AGENTS.md`
- `小説/`
- `小説/第001章/`
- `小説/第001章/本文.txt`
- `小説/第001章/章内プロット.md`
- `設定/`
- `設定/登場人物.md`
- `設定/世界観.md`
- `設定/用語集.md`
- `プロット/`
- `プロット/全体構成.md`
- `資料/`
- `メモ/`

章は`小説/第001章/`のようなゼロ埋め連番ディレクトリとして管理する。章タイトルはディレクトリ名には含めず、`本文.txt`や`章内プロット.md`の本文内に書く。小説本文はMarkdown記法を前提にしないプレーンテキストとして`本文.txt`へ置き、章内プロットや設定資料など構造化したメモはMarkdownファイルに置く。

ユーザー定義テンプレートは、新規ワークスペース作成時に繰り返し使うための軽量な雛形として扱う。MVPでテンプレートに含められる項目は以下だけとする。

- ワークスペース直下または一層ディレクトリ直下に作成するディレクトリ
- ワークスペース直下、一層ディレクトリ直下、または二層ディレクトリ直下に作成するテキストファイル

テンプレート内ディレクトリは二層まで作成できる。`小説/第001章/下書き/`のような三層以上のディレクトリ作成はMVP対象外とする。テキストファイルは二層ディレクトリ配下まで置けるが、さらに深い階層には置けない。

テンプレートエディターページを用意する。

- 左端サイドバーからテンプレート管理ページへ移動できる。
- ルートは`/templates`とする。
- テンプレート一覧、テンプレート新規作成、名前変更、削除、項目追加、項目削除、テキストファイル本文編集ができる。
- ディレクトリ項目は名前だけを編集できる。
- ファイル項目はパスと本文を編集できる。
- テンプレート適用前に、作成予定のディレクトリとファイルの一覧を確認できる。
- テンプレート管理ページはエディット画面の3ペインレイアウト内に表示しない。

テンプレート選択UIを用意する。

- 新規ワークスペーステンプレートを適用する操作では、アプリ内定義テンプレートとユーザー定義テンプレートから1つ選択できる。
- テンプレートを選択せず、空のワークスペースとして開始する選択肢も用意する。
- 選択中テンプレートの作成予定項目を適用前に表示する。
- 既存ワークスペースを開く操作では、テンプレートを自動適用しない。

テンプレート適用のルール:

- 適用先は検証済みのアクティブワークスペースルート配下に限定する。
- テンプレート内の各パスも、ワークスペースルート基準で正規化し、ワークスペース外へ抜けるパスを拒否する。
- `.`から始まるセグメントを含むテンプレートパスは拒否する。
- テンプレート内のディレクトリは二層までとし、三層以上のディレクトリパスを拒否する。
- テンプレート内のファイルパスは、ワークスペース直下、一層ディレクトリ直下、または二層ディレクトリ直下だけ許可する。
- テンプレート内のファイル本文はテキストとして扱える内容だけ許可し、NULLバイトを含む内容は拒否する。
- 既存祖先ディレクトリがシンボリックリンクの場合、実体パスがワークスペース外へ出るなら拒否する。
- 既存ファイルはユーザー承認なしに上書きしない。`AGENTS.md`などテンプレートファイルが既に存在する場合は、衝突エラーとして適用を止める。
- 既存ディレクトリは作成済みとして扱ってよいが、その配下へ作成する前にシンボリックリンク脱出検証を行う。
- 適用後はファイルツリーを更新する。

ユーザー定義テンプレート保存のルール:

- テンプレート定義はアプリのメタデータとして保存し、ワークスペース内ファイルには保存しない。
- テンプレート定義の読み込み、保存、削除APIはZodで入力を検証する。
- テンプレート名は空文字を拒否する。
- テンプレート内のパスは保存時と適用時の両方で検証する。
- テンプレート内にAPIキーなどのシークレットを保存しないようUIで注意喚起してよいが、通常のテキスト本文として保存される点はユーザー操作に委ねる。

## モード構成

アプリケーションは、執筆スタイルの異なる3つのモードを持つ。モードは左端サイドバーのアイコンから、TanStack Startのルート遷移として切り替える。

- チャットモード: AIとの会話を主体に小説を書き進めるモード。新規ユーザーの既定モードとする。
- エディットモード: 3ペイン（ファイルツリー、エディター、AIアシスト）で、人間が原稿を直接編集しながら局所的なAI処理を利用するモード。
- リーダーモード: 書き上げた本文を読むための読書専用モード。

モード共通のルール:

- 作品の状態の正はワークスペース内のファイルとする。モード専用の不可視データストアを作らない。
- チャットモードでファイルツリーを表示しなくても、エディットモードへ切り替えれば同じワークスペースの全ファイルを確認できる。
- 会話履歴はチャットモードだけで扱う。エディットモードのAIアシストは会話を作成せず、実行中の状態と今回の結果だけを右ペインへ表示する。
- チャットモードのAI編集は自動適用を既定とし、エディットモードのAIアシストが作成した編集案は必ずユーザー承認制にする。
- ワークスペース単位で、最後に開いた作業モード（チャットモードまたはエディットモード）を記録する。リーダーモードは作業モードとして記録しない。
- 前回作業モードの記録はクライアント側のUI設定として`localStorage`へ保存する。不正または古い保存値は安全な既定値（チャットモード）へフォールバックする。
- `/`は前回作業モードのルートへ遷移する。記録がない場合はチャットモードへ遷移する。

### チャットモード

チャットモードは、AIチャット上で小説を書いている層を主対象にした会話主体の画面とする。ルートは`/chat`とする。

- 会話UIを画面全面に表示し、ファイルツリーとエディターペインは表示しない。
- チャット入力、LLMプロフィール選択、コンテキスト使用率表示、ツール実行表示などの会話機能を画面内に提供する。
- チャットモードを開いたとき、会話履歴の最新メッセージが見える位置まで自動スクロールする。ユーザーが最新付近にいる場合は新規メッセージ、ストリーミング応答、ツール実行表示、編集提案カードの追加に追従するが、過去ログ閲覧のために上へスクロールしている場合は強制的に最下部へ戻さない。
- ワークスペース操作ヘッダーを表示する。ワークスペースを開く、新しい小説を始める、現在のワークスペース表示を含める。
- 「新しい小説を始める」は、フォルダ選択とチャットモード用テンプレート適用を1つの流れに畳んだ導線とする。テンプレートの概念を前面に出さない。
- AIが小説の進め方、プロット、ディレクトリ構成を管理する前提の専用システムプロンプトを持つ`AgentProfile`を使う。
- チャットモード用テンプレートは内蔵テンプレートとして定義し、章構成は標準テンプレートと互換の構成（`小説/第00X章/`のゼロ埋め連番など）を維持する。
- チャットモード管理用のメタ情報が必要な場合は、規約から導出できない情報に限定したJSONファイル程度に留める。エディットモードとリーダーモードはメタ情報ファイルがなくても動作する。
- 保存済み会話の表示、会話切り替え、新規会話作成、ストリーミング応答、ツール実行状況、編集提案カードを提供する。
- 同じワークスペースのまま別画面へ移動してもチャットのAI応答を継続する。チャットへ戻った際は進行中の応答・実行状態または完了結果を引き継ぐ。
- 別画面の表示中にAI応答が完了・失敗した場合、サイドバーのチャットにチェックまたは感嘆符の印を付ける。色に加えて形と読み上げ用の説明で区別し、チャットを開くと消す。チャット表示中の完了や履歴の初期読み込みでは通知しない。
- 実行状態と通知はアプリ内の現在ワークスペースのセッションで保持し、ワークスペース変更時にはリセットする。アプリ終了・再読み込み後の実行状態復元、OS通知、会話ごとの未読通知は対象外とする。
- 新規会話の案内は初回メッセージの送信前だけ表示し、最初のターンを開始した時点で非表示にする。
- OSのファイルマネージャーからドロップされたテキストファイルは、チャット本文への文字列挿入とは区別してコンポーザーの添付チップとして表示する。チャットモードへファイルツリーなどの左ペインは追加しない。
- 添付はUTF-8として厳格に検証し、NULLバイト、1件1MiB超過、合計2MiB超過、6件以上を拒否する。送信前は個別に削除でき、送信失敗時は再送できるよう保持し、送信成功、会話切り替え、新規会話、ワークスペース切り替えで入力用添付を破棄する。
- 添付ファイルは`vercel-ai`実行方式のチャットだけで利用できる。旧Codex会話への追加実行は拒否する。
- 送信された添付の原バイトは`{dataRoot}`配下の要求単位の一時領域へ保存し、モデルへ本文や一時pathを直接渡さずopaque ID、元ファイル名、byte数だけを知らせる。AIは専用toolで内容を読み、ワークスペース内の新規保存先を決める。
- 添付ごとに処理中、配置済みと保存先、未配置、配置失敗を表示する。配置済みファイルは通常のチャットモードCreate proposalとして適用済みカードとUndoを提供する。
- 要求終了時の未配置ファイル、配置済みファイル、失敗したファイルは一時領域から削除する。期限切れ・中断・再起動後の孤児もbounded cleanupし、workspace ID、conversation ID、request IDが一致しない参照は拒否する。
- メッセージコンポーザーでは利用可能なChatGPTプランまたはAPIキー接続のLLMプロフィールを選択でき、利用不可の選択肢には理由を表示する。
- 最新のmain role入力コンテキスト使用率とAIセッション累計を別指標として表示し、usage不明を0%と誤表示しない。出力上限到達時は応答が途中で止まった可能性を表示する。
- assistantターンのtool履歴は既定でサマリー表示とし、個別履歴を展開できる。編集提案のdiffとApply状態はtool履歴内へ埋め込まず、独立した提案カードとして表示する。
- 実行中はモデルから提供された推論テキスト・推論要約を「推論の途中経過」として回答本文と分けて表示する。既定は最新160文字のプレビューとし、展開して直近最大12,000文字を読める。表示は現在の実行だけの一時状態とし、会話JSONや次ターンのモデル入力へ追加せず、完了・失敗・会話切り替え・ワークスペース変更時に消去する。同じワークスペース内の画面移動中は受信を継続する。モデルによって推論は届かず、更新間隔や完全性も保証しない。未受信時は生成中表示と案内を表示し、進捗内容を捏造しない。
- `/compact`と`/圧縮`の会話圧縮コマンド、および設定ページの自動圧縮ON/OFFと50%から90%の閾値設定を提供する。メッセージ先頭で`/`から空白なしで入力している間は、コンポーザー直上に利用可能なコマンド名、alias、説明を前方一致で絞り込んで一行のコンパクトな候補として表示する。幅が不足する場合は説明を省略し、コマンド名とaliasを優先する。候補はキーボードまたはポインターで選択して入力欄へ設定できるが、選択だけでは実行しない。詳細な圧縮契約は「会話履歴のコンテキスト圧縮」に従う。

チャットモードのAI編集:

- チャットモードから送信したチャットでは、`Edit`、`Create`、`CreateDirectory`の提案を承認なしで自動適用することを既定とする。
- チャットモードの自動適用はproposal toolが成功した時点で行い、同一turn内の後続toolが先行proposalの適用結果を利用できるようにする。`CreateDirectory`とその配下への`Create`など依存するproposalはtool実行順に適用し、会話履歴には各proposalの適用結果とUndo用snapshotを同じ順序で保存する。
- 同一turn内の後続proposalが失敗またはconflictになった場合も、先に成功したproposalは実ファイルと一致する`applied`状態として会話へ残す。取り消しは依存関係の逆順で1件ずつ行い、childが残るdirectoryの取り消しはconflictとして安全に拒否する。
- 自動適用でも、ワークスペース境界、パス検証、`.`始まりセグメント拒否、conflict確認などの既存の安全ルールを維持する。
- 自動適用された編集は、適用済みカードとして会話内へ表示し、会話履歴にも残す。
- 適用済みカードから、少なくとも直近の適用を取り消して適用前の内容へ復元できる。取り消しのために、Apply時に適用前の内容を保持する。Git連携は引き続きMVP対象外とする。
- エディットモードで対象ファイルが未保存状態の場合は、既存ルール通りApply不可として扱う。

チャットモードで利用するLLMは開発者側で制限しない。ローカルLLMなどツール対応が弱いモデルでツール呼び出しの失敗が続く場合は、選択中のモデルがチャットモードに不向きな可能性が分かるエラー表示を行う。

### エディットモードのAIアシスト

エディットモードの右ペインは、会話ではなく、現在の原稿へ目的の決まった処理を1回ずつ実行するAIアシストとする。

- 組み込みアシストとして、少なくとも「推敲」「校正」「ルビ候補」を提供する。
- アシストの対象はCodeMirrorの選択範囲を優先し、選択範囲がなければ現在開いているファイル全体とする。対象ファイルまたは対象文字列がない場合は実行できない。
- 各アシストは、名前、説明、AIへの固定指示、対象種別、結果種別、組み込みかユーザー定義かを表す共通のアシスト定義として扱う。組み込みアシストを個別のUI分岐だけで実装しない。
- ユーザーは実行時に1行の「追加指示（任意）」を入力できる。空文字または空白だけの場合は追加指示なしとして、アシストの固定指示だけで実行する。
- 追加指示は今回の実行にだけ適用し、アシストの固定指示、アプリ共通の安全規則、対象範囲を置き換えない。API入力はZodで検証し、文字数上限を500文字とする。
- 「推敲」は文章表現を改善する編集案、「校正」は誤字脱字や明確な文法上の問題を直す編集案、「ルビ候補」は既存のルビを尊重し、設定資料や用語集に読みがあれば優先して、リーダーモード互換の`｜親文字《ルビ》`形式による編集案を作成する。
- AIアシストは単発実行とし、実行結果を次の実行の会話文脈として暗黙に引き継がない。必要な原稿、選択範囲、設定資料は実行ごとに明示的に構成する。
- 編集結果は既存の編集提案と同等のdiffとして表示し、ユーザーが1件ずつApplyまたはRejectする。承認前は直接ファイルへ書き込まない。適用後は今回の結果カードからUndoでき、適用前の全文へ戻す。未保存変更や外部変更時は拒否・conflictとし、別のファイルや画面への移動後まで結果カードの保持は保証しない。
- 対象ファイルに未保存の変更がある場合は実行不可とし、先に保存または変更破棄を求める。実行後からApplyまでに対象内容が変わった場合はconflictとして拒否する。
- 右ペインは従来どおり折りたたみ、再表示、横幅変更ができる。折りたたみ状態やペイン幅の既存挙動を維持する。
- AIアシストで利用するモデル選択は既存のChatGPTプランまたはAPIキー接続のLLMプロフィールの安全な選択境界を再利用する。実行方式を問わず、AIアシストの対象と結果形式を同じ契約に揃える。
- 右ペインのモデル選択UIは、チャットモードと同じく「実行方式」と「モデル」の2段階選択とする。標準モデルではプロフィール、provider、モデルの分類・表示名・利用不可理由をチャットモードと同じコンポーネント境界で表示する。ChatGPTプランでは認証済みモデル一覧を表示する。
- AIアシストの接続・モデル選択は専用の`localStorage`へ保存し、画面移動・再読込で復元する。チャット設定やLLMプロフィール設定は変更しない。利用不可でも明示選択を保持し、別接続へ自動変更しない。選択変更はローカルstateへ同期的に反映する。SIWC有効時の新規利用者はChatGPTプランを既定とし、APIキー接続では現在の`writing`ロールを初期値とする。
- 標準モデルの既定値は現在の`writing`ロール割り当てとする。右ペインで選んだプロフィールまたはprovider・モデルは今回のAIアシスト実行にだけ反映し、`main`ロール、チャットの保存済みモデル選択、LLMプロフィール設定を変更しない。
- 標準モデルの実行入力は`default-writing`、`profile` override、`model` overrideを判別可能なdiscriminated unionとし、サーバー側で利用可否とAPIキー境界を検証してからmodel providerを生成する。モデルoverrideは解決済み`writing`ロールのtemperatureとmaxOutputTokensを継承する。

ユーザー定義アシスト:

- ユーザーは、名前、説明、AIへの固定指示、対象種別、結果種別、追加指示欄のプレースホルダーを持つカスタムアシストを作成、編集、削除できる。結果種別はユーザー向けの日本語ラベルと説明付きの選択肢から選び、保存値はZodスキーマで検証したサポート対象の値のみを受け付ける。
- カスタムアシストは組み込みアシストと同じ実行経路、対象判定、未保存判定、編集承認、conflict確認を使う。
- カスタムアシストは保存済みプロンプトとして扱い、AI tool権限、system prompt、アプリ共通の安全規則を追加または上書きできない。
- カスタムアシスト定義はアプリのメタデータとして保存し、ワークスペース内ファイルや会話履歴には保存しない。名前と固定指示の空文字を拒否し、保存・読み込み・削除APIをZodで検証する。
- 組み込みアシストは編集・削除できない。カスタムアシストがなくても組み込みアシストだけでAIアシストを利用できる。

### リーダーモード

リーダーモードは、ワークスペース内の小説本文を読むための読み取り専用画面とする。ルートは`/reader`とする。

- 章一覧は`小説/`配下のゼロ埋め連番ディレクトリ（`小説/第00X章/`）から導出する。専用のマニフェストファイルを必須にしない。
- 章タイトルは各章の`本文.txt`の先頭の空でない行から導出し、導出できない場合はディレクトリ名を表示する。
- 章の本文は`本文.txt`を読み取り専用で表示する。
- 本文表示時は、ワークスペース内の本文ファイルを変更せずに、代表的ななろう・カクヨム互換ルビ記法（`｜親文字《ルビ》`、`|親文字《ルビ》`、`漢字列《ルビ》`）をHTMLの`ruby`相当で表示する。
- 本文表示時は、カクヨムの傍点記法（`《《文字》》`）を傍点付きテキストとして表示する。
- 前後の章への章送り操作を提供する。
- 表示中の章本文をコピーできる導線を提供する。
- 章本文内の空でない選択を右クリックすると「エディットモードで開く」を表示し、表示tokenが保持する原文UTF-16オフセットを使って対象`本文.txt`の正確な範囲をCodeMirrorで選択、スクロール、フォーカスする。文字列検索による再特定は行わない。
- 通常文、複数行、サロゲートペア、ルビ3形式、傍点の表示選択を原文範囲へ対応付ける。`rt`だけ、章をまたぐ選択、タイトルや操作UIを含む選択など安全に対応できない場合は操作を表示しない。
- ジャンプ要求はpath、開始・終了offset、検証用原文断片を一時的なクライアント状態で渡し、永続化しない。対象ファイルの未保存内容は維持し、原文断片が一致しない場合はファイルを開いた上で選択ジャンプだけを中止して理由を表示する。
- リーダーモードからファイルの編集・保存はできない。
- ワークスペース未選択の場合は、ワークスペースが開かれていない旨の案内と、チャットモードまたはエディットモードへの誘導を表示する。
- 章ディレクトリまたは`本文.txt`が存在しない場合は、まだ読める本文がない旨の案内を表示する。

## 画面構成

アプリケーションは、左端に細いサイドバーを持つアプリシェルで構成する。サイドバーからTanStack Startのページルーティングでチャットモード画面、エディット画面、リーダーモード画面、テンプレート管理ページ、LLMプロフィール管理ページ、設定ページを切り替えられる。

ページ構成:

- `/` は前回作業モードのルートへ遷移する。記録がない場合はチャットモードへ遷移する。
- `/chat` はチャットモード画面を表示する。
- `/editor` はエディット画面を表示する。
- `/reader` はリーダーモード画面を表示する。
- `/settings` は設定ページを表示する。
- `/templates` はテンプレート管理ページを表示する。
- `/llm-profiles` はLLMプロフィール管理ページを表示する。
- 左端サイドバーはルートレイアウトに置き、現在のルートに応じた選択状態を表示する。
- 左端サイドバー最下部に、`package.json.version`を正本とした現在のアプリケーションバージョンを控えめに表示する。内部のpreview表記はUI向けに読みやすく整形し、クリック時は設定ページへ遷移してよい。
- ワークスペースを開く、現在のワークスペース表示、新規ワークスペーステンプレート適用などのワークスペース操作ヘッダーはエディット画面とチャットモード画面に表示し、設定ページ、テンプレート管理ページ、LLMプロフィール管理ページ、リーダーモード画面には表示しない。チャットモード画面のヘッダー構成は「モード構成」のチャットモード定義に従う。
- エディット画面では、ワークスペースの末尾フォルダ名を小説タイトルとしてヘッダーとファイルツリーペインに表示する。絶対パスは常時表示せず、小説タイトルのツールチップで確認できるようにする。
- 既存の`/api/*`エンドポイントは当面維持してよい。TanStack Start Server Routesへの移行は別途検討する。

エディット画面は3つのリサイズ可能なペインで構成する。

各ペインは独立してスクロールできるようにする。左ペインのファイルツリー、中央ペインのエディター、右ペインのAIアシストは、それぞれの内容がペイン高を超えた場合にペイン内だけでスクロールし、他ペインのスクロール位置に影響しない。

1. 左端サイドバー
   - アプリ全体の左端に細く固定表示する。
   - チャットモード画面、エディット画面、リーダーモード画面、テンプレート管理ページ、LLMプロフィール管理ページ、設定ページへ移動できるアイコンボタンを表示する。
   - 現在表示中の画面が分かる選択状態を表示する。
   - サイドバーはファイルツリーペインのリサイズ対象に含めない。
   - 画面切り替えはTanStack Startのルート遷移として扱い、単一コンポーネント内のクライアント状態だけでページを切り替えない。

2. ファイルツリーペイン
   - ヘッダー左端のアイコンボタンでペイン全体を折りたためる。
   - 折りたたみ中は、中央エディターペインのタブヘッダー左端にファイルツリーペインを再表示するアイコンボタンを表示する。
   - アクティブなワークスペース配下のファイルとディレクトリを表示する。
   - ファイルとディレクトリはワークスペース相対パスのフラット一覧ではなく、階層構造として表示する。
   - ディレクトリの展開・折りたたみに対応する。
   - ディレクトリ行はファイル行と視覚的に区別でき、子要素は階層に応じてインデントされる。
   - ファイルまたはディレクトリの右クリック、行末メニュー、キーボード操作から、対象項目付近にフローティングのコンテキスト操作メニューを表示する。メニューはツリーの通常フローを押し下げず、右クリック時はポインター位置、行末メニュー時はボタン位置を基準に表示する。
   - ディレクトリ配下へのファイル作成・ディレクトリ作成と項目の名前変更では、対象行をインライン編集として表示し、ファイル名またはディレクトリ名のみを入力する。ツールバーから開始した作成操作はワークスペース直下を対象としてツリー先頭付近にインライン入力を表示する。
   - 作成・名前変更のインライン入力の外側をクリックした場合は、未実行の入力を閉じる。入力欄内の入力・送信操作は外側クリックとして扱わない。
   - ファイルを選択すると、選択中のファイルがツリー上で分かるように表示する。
   - ファイル名フィルターに対応する。
   - フィルター時は一致したファイルまたはディレクトリだけでなく、一致項目へ到達するために必要な親ディレクトリも表示する。
   - `.git`、`node_modules`、`dist`、`.data`などのノイズになりやすいディレクトリは既定で非表示にする。
   - MVPでは表示するファイル数の上限を100件にする。上限を超えた場合は、フィルターや検索で絞り込む導線を出す。
   - `章内プロット.md`、`概要.md`、`メモ.md`などの章ごとの参考ファイルは通常ファイルとして表示し、ユーザーが開いて編集できるようにする。これらをAI専用の隠しファイルとして扱わない。
   - 同じ親ディレクトリの兄弟ファイル行の間へ外部テキストファイルをドロップできる。行間インジケーターを表示し、`A`と`B`の間へ`C`をドロップした場合は同じディレクトリへ`C`を新規作成して`A, C, B`の順で表示する。
   - 複数ファイルは`DataTransfer.files`の順で連続配置する。同名conflictでは上書きや自動リネームをせず、フィルター中、100件上限による省略中、異なる親の境界では行間ドロップを無効にする。
   - ファイル間の手動順序はworkspaceごとのアプリメタデータとして`{dataRoot}`へ保存し、workspace内へ隠しファイルを作らない。ディレクトリはファイルより前に表示し、順序指定のないファイルは決定的な既定順とする。名前変更と削除では順序pathも追従または除去する。

3. エディターペイン
   - CodeMirrorを使う。
   - 選択したファイルをテキストとして開く。
   - 行番号は既定で非表示にし、設定ページのUI設定から表示へ切り替えられるようにする。
   - 未保存状態を追跡する。
   - 明示的な保存操作に対応する。
   - AI編集の手動適用、チャットの自動適用結果の受信、取り消しに応じ、開いている全タブの保存済み内容を再確認する。非選択タブと他モードの表示中も対象とし、更新で選択タブを切り替えない。
   - 未保存内容は再確認中に始めた入力も含めて保持する。保存済みファイル側にも変更がある場合は競合を表示し、通常保存を止める。必要な文章をコピーできる状態を維持し、確認付きの「更新内容を読み込む」で未保存内容を破棄して反映できる。OS上の外部編集の常時監視は対象外。
   - OSからCodeMirrorへドロップしたUTF-8テキストファイルは、既存選択を置換せずドロップ座標のdocument位置へ`DataTransfer.files`順に1 transactionで挿入する。挿入末尾へcaretを移動し、通常の未保存変更とUndo/Redoとして扱い、自動保存しない。
   - Readerから渡された一時ジャンプ要求は対象ファイル読込後に原文断片を検証し、正しい場合だけ指定offsetを選択して表示位置へスクロールし、CodeMirrorへフォーカスする。同じ要求は1回だけ消費する。

4. AIアシストペイン
   - 現在の対象が選択範囲かファイル全体かを表示する。
   - 利用可能な組み込みアシストとユーザー定義アシストを表示する。
   - 1行の「追加指示（任意）」入力欄と実行ボタンを表示する。
   - 実行中状態、エラー、編集提案diff、Apply、Rejectを表示する。
   - AIアシストは設定ページのプロフィールを候補として使い、接続・モデルの選択は独立して保持する。SIWC未ログイン時もChatGPTプランを選択でき、設定へ案内する。
   - APIキー未設定などで利用不可のプロフィールやモデルは選択不可にし、利用不可理由を表示する。

5. テンプレート管理ページ
   - 左端サイドバーのテンプレートアイコンから表示できる。
   - テンプレート管理ページは`/templates`の通常ページとして表示する。
   - テンプレート管理ページはエディット画面の3ペインレイアウト内に表示しない。
   - ユーザー定義テンプレートの一覧、作成、編集、削除ができる。
   - テンプレートに追加できる項目は、二層までのディレクトリと三層までのテキストファイルだけに限定する。
   - 保存前にテンプレート名、パス、階層、テキスト本文の基本検証結果を表示する。
   - アプリ内定義テンプレートは閲覧・複製できてよいが、直接編集または削除はできない。

6. LLMプロフィール管理ページ
   - 左端サイドバーのモデルまたはLLMアイコンから表示できる。
   - LLMプロフィール管理ページは`/llm-profiles`の通常ページとして表示する。
   - LLMプロフィール管理ページはエディット画面の3ペインレイアウト内に表示しない。
   - LLMプロフィール管理ページでは、`/api/llm/providers`が返す許可済みprovider/model一覧だけを使って、ユーザー定義LLMプロフィールを表示・作成・編集・削除できる。
   - LLMプロフィールは、名前、provider、model、temperature、最大出力トークン数、任意のコンテキスト長上書きなど、モデル実行に必要なユーザー向け設定をまとめたものとして扱う。
   - 内蔵プロフィールは内部デフォルトやフォールバックとして扱い、プロフィール一覧やチャットのプロフィール選択肢には表示しない。既に内蔵プロフィールが割り当てられている場合、UI上はそのプロフィールが指すprovider/modelのモデル選択として表示する。
   - 内蔵プロフィールは直接編集または削除できない。必要に応じて複製してユーザー定義プロフィールを作成できてよい。
   - 用途別割り当て設定では、通常チャット、執筆・推敲、軽作業、検索サブエージェントに使うLLMプロフィールまたはprovider/modelを選択できる。内部デフォルト割り当てはUIで前面に出さない。
   - APIキー未設定などで利用不可のプロフィールは選択不可にし、利用不可理由を表示する。
   - 設定ページにあるAPIキー管理への導線を表示してよいが、APIキー本文の入力・保存・削除は設定ページ側で扱う。
   - LLMプロフィール管理ページではAPIキー本文、base URL、その他シークレット値を表示・保存しない。
   - LLMプロフィールと用途別割り当てはクライアント側の`localStorage`に保存する。不正、古い、または現在の許可済みprovider/model一覧に合わない保存値は安全な既定値へフォールバックする。旧形式の`Record<role, string>`保存値は後方互換で読み込める。

7. 設定ページ
   - 左端サイドバーの設定アイコンから表示できる。
   - 設定はモーダルではなく`/settings`の通常ページとして表示する。
   - 設定ページはエディット画面の3ペインレイアウト内に表示しない。
   - LLM APIキーは設定ページから入力・保存・削除できる。ただし、APIキー本文をクライアント側の永続ストレージへ保存してはならない。
   - 保存済みAPIキーは再表示しない。設定ページでは、providerごとの「設定済み / 未設定」と、必要な場合だけ末尾4文字などの非機密メタデータを表示する。
   - providerごとのAPIキー入力一覧は初期状態で閉じ、アクセシブルな開閉操作で必要なときだけ表示する。開閉状態は永続化しない。
   - 設定ページでは、現在の用途別LLMプロフィール割り当ての概要を表示してよい。ただし、プロフィールの作成・編集・削除と用途別割り当ての変更はLLMプロフィール管理ページで行う。
   - 設定ページ下部にアプリ情報として、`package.json.version`をUI向けに整形した現在のアプリケーションバージョンを表示する。
   - base URLなどの高度な接続設定はMVPでは環境変数のみで扱い、設定ページから入力・保存・表示しない。
   - UI設定として、エディターの行折り返し、左ペインのノイズディレクトリ表示、最後に開いたワークスペース復元、会話の自動圧縮ON/OFFと自動圧縮閾値を切り替えられる。
   - 自動圧縮閾値はコンテキスト使用率50%から90%の範囲で設定する。既定は70%とする。
   - UI設定はクライアント側の`localStorage`に保存する。不正または古い保存値は安全な既定値へフォールバックする。
   - `localStorage`にはAPIキー、base URL、その他シークレット値を保存しない。

## ファイル取り扱い

対象可否の判断に拡張子は使わない。

サーバーは以下の安全策を入れた上で、ファイルをテキストとして扱う。

- ローカルFS上のワークスペース操作は`WorkspaceFileStore`境界越しに扱う。MVPではローカルFS向けの関数実装のみを用意し、SQLite/D1などの仮想ファイルストアは将来拡張とする。
- ファイルストア境界はOOPライクなクラスインスタンスより、FPライクな`WorkspaceFileContext`と関数群を優先する。feature層はcontextとワークスペース相対パス、テキスト操作の意図を明示的に渡す。
- ローカルFS向け実装は`realpath`、シンボリックリンク脱出検証、OS絶対パス解決などのローカルFS固有処理を境界内に閉じ込める。
- サンプル内容にNULLバイトを含むファイルは拒否または非表示にする。
- 直接エディターで開くには大きすぎるファイルを拒否する。
- 読み取り不能なファイルには明確なエラーを返す。
- OSドロップ入力は拡張子やMIME typeだけで判定せず、件数、個別・合計byte数、canonical Base64、厳格なUTF-8 decodeとbyte roundtrip、NULLバイトを検証する。不正な入力ではエディター本文、workspace、表示順メタデータを変更しない。
- ファイルツリーへのドロップ取り込みは専用APIと`WorkspaceFileStore`境界を通し、workspace root、正規化済み相対path、`.`始まりsegment、symlink脱出、既存ファイルをサーバー側で再検証する。
- すべてのパスをワークスペースルート基準で正規化・検証する。
- ワークスペース相対パスは、UI、APIレスポンス、クライアント状態、AIツール入出力、テンプレート定義ではOSに関係なくPOSIX風の`/`区切りで扱う。
- Windows由来の`\`区切りで入力されたワークスペース相対パスは、共通のパス検証境界で`/`区切りへ正規化してから、階層上限、`.`始まりセグメント、ワークスペース外脱出を検証する。
- 実ファイルアクセス時だけ、正規化済みのワークスペース相対パスからOSネイティブの絶対パスを組み立てる。`path.join`、`path.normalize`、`path.relative`などのOS依存戻り値をそのままUI、API、AIツールへ公開してはならない。
- テンプレート保存、適用前プレビュー、適用API、ファイルツリー、エディター、AI編集提案、`Read`、`Glob`、`Grep`、`Search`は同じワークスペース相対パス正規化と検証結果を使う。
- MVPではワークスペース相対パスのいずれかのセグメントが`.`から始まるファイルは編集不可にする。
- `.`から始まるファイルやディレクトリは、必要に応じて検索・読み取り対象にはできるが、`Edit`とエディター保存では拒否する。
- ワークスペース直下の`AGENTS.md`は通常のテキストファイルとして扱い、ユーザーもエージェントも閲覧・編集できる。エージェントによる編集は他のファイルと同じく承認制にする。
- ファイルツリーで一度に扱うファイル数の上限は100件にする。
- AIの`Read`で返す内容は最大2000行にする。超過時は切り詰めたことを明示する。
- `Grep`と`Search`の返却件数は最大10件にする。

## AIエージェント

AIエージェントはサーバー上で実行する。クライアントへAPIキーを渡してはならない。

AI呼び出し、ストリーミング、ツール呼び出しはVercel AI SDKと共通の`runAgentLoop`で実行する。接続方式を暗黙に切り替えない。

LLMプロバイダーはOpenAI、DeepSeek、Gemini、Anthropic、OpenAI互換APIを切り替えられるようにする。OpenAI互換APIはLM Studio、OpenRouter、llama.cpp serverなどのOpenAI Chat Completions互換エンドポイントを対象にし、本家OpenAI providerとは混ぜず独立したproviderとして扱う。APIキーはサーバー側だけで扱い、クライアントへ渡してはならない。クライアントから送信できるのは、サーバーが許可したLLMプロフィールID、プロフィール作成・編集に使う`providerId`と`modelId`、provider種別に応じて許可されたbase URLなどの接続設定、および設定ページから保存・削除するためのAPIキー入力値のみとする。

### SIWC Responses直接接続（実験版）

設定の通常ログイン操作は1つに統一する。未登録・サインアウト時は「ChatGPTでログイン」、期限切れ・再認証必要・推論許可不足時は「もう一度ログイン」、有効なサインイン済み状態では「ログアウト」を表示する。選択中の登録があればログイン時に再利用する。利用画面は単一のChatGPT接続を扱い、アカウント切替・別アカウントの追加は提供しない。別アカウントを利用する場合はログアウト後にログインする。認証切れ・推論許可不足時にもログアウトを提供する。認証処理中は重複開始を防ぎ、キャンセルを提供する。

SIWCの認証・Responses直接接続・設定UIを実験版として実装する。既定は無効とし、開発者が`GHOSTWRITER_ENABLE_SIWC_PREVIEW=1`を指定した場合のみ表示・利用可能にする。詳細は[SIWC直接接続仕様](siwc-responses-migration.md)、確認済み事項と公開前の残作業は[検証と公開状況](../docs/siwc-validation-status.md)で管理する。APIキー接続を維持する。旧Codex CLI連携は撤去済み。

製品の接続導線は「ChatGPTでログイン」を主とする（タスク230）。SIWC有効時、新規利用者のチャット・AIアシストではChatGPTプランを初期選択とし、ログインから利用可能モデルの選択・送信へ進める。APIキー接続は任意の追加接続として提供する。既存利用者が明示した設定と保存済み会話の接続は優先し、ログインだけで上書きしない。未対応OS・preview flag無効時には利用可能と表示せず、一般公開の既定ONは229の公開ゲートに従う。

SIWCは`vercel-ai`内部の`openai-chatgpt` providerとして既存runAgentLoop・編集サービスを使用する。新規会話をアカウントに紐付け、旧Codex会話は履歴閲覧と既存編集案のApply/Undoを維持し、追加AI実行・圧縮は拒否する。旧接続設定は廃止を案内し、新しい会話で接続を明示選択させる。外部CLIやその資格情報は削除しない。失敗時・サインアウト時にAPIキー接続へ自動変更しない。SIWC会話の既定各roleは選択中のSIWCモデルを使い、AIアシスト・手動/自動圧縮もstream方式で実行する。編集承認・自動Apply・Undo規則は共通。

全stepのtool履歴と必要な暗号化reasoningをassistantメッセージへ保存し、同じアカウントだけで再利用する。圧縮境界以前は要約から再開する。資格情報は専用dataRootに保存し、その保存ディレクトリを含む/内包されるワークスペースは認証方式を問わず拒否する。Windowsでは実行ユーザーSIDだけに許可するACLで保存先を作成し、読み書き時にも所有者・権限・reparse pointを検証する。広い既存ACLを自動修復して利用しない。Windowsの認証ブラウザは検証済みauth.openai.comのHTTPS URLをOSの関連付けで開く。Windowsの実OAuth・配布版callbackを含む229の公開ゲートを満たすまで既定の公開は行わない。

環境変数の読み込みはサーバー起動時またはAPIハンドラー生成時の小さな設定読み込み境界に集約する。LLMプロバイダー生成、モデル選択、利用可能モデル一覧の判定では`process.env`や`NodeJS.ProcessEnv`を直接扱わず、読み込み済みのアプリ設定オブジェクトとシークレットストア境界を注入して使う。

LLM APIキー保存はサーバー側の`LlmSecretStore`境界に集約する。対象OSはmacOSとWindowsのみとし、macOSではKeychain、WindowsではCredential Managerを使う。LinuxはMVP対象外とし、OSシークレットストア保存APIは明確な未対応エラーを返す。

APIキー解決の優先順位は実行形態で変わる。

- Web開発版と`desktop:dev`: 環境変数 → OSシークレットストア → 未設定
- デスクトップ配布版: OSシークレットストア → 未設定

デスクトップ配布版では、Finderやスタートメニューから起動したGUIアプリへシェル環境変数が一致して渡らないため、LLM APIキー環境変数（`DEEPSEEK_API_KEY`、`OPENAI_API_KEY`、`GOOGLE_GENERATIVE_AI_API_KEY`、`ANTHROPIC_API_KEY`、`GHOSTWRITER_OPENAI_COMPATIBLE_API_KEY`）は参照しない。sidecarは配布版起動時に`GHOSTWRITER_RUNTIME_MODE=desktop-packaged`を受け取り、このモードでは`LlmSecretStore`とprovider設定へLLM APIキー環境変数を渡さない。base URL、既定provider/model、sidecar認証、アプリデータディレクトリ、同梱`ripgrep`などAPIキー以外の`GHOSTWRITER_*`環境変数は従来どおり利用できる。

Web開発版と`desktop:dev`では、環境変数で指定されたAPIキーは引き続き利用でき、シークレットストアより優先する。

`LlmSecretStore`は少なくとも以下の操作を提供する。

```ts
type LlmSecretProviderId = "openai" | "deepseek" | "gemini" | "anthropic" | "openai-compatible";

type LlmSecretStatus = {
  providerId: LlmSecretProviderId;
  source: "env" | "system" | "missing";
  isConfigured: boolean;
  maskedSuffix?: string;
  canUpdate: boolean;
  canDelete: boolean;
};

type LlmSecretStore = {
  getApiKey(providerId: LlmSecretProviderId): Promise<string | null>;
  getStatus(providerId: LlmSecretProviderId): Promise<LlmSecretStatus>;
  setApiKey(providerId: LlmSecretProviderId, apiKey: string): Promise<void>;
  deleteApiKey(providerId: LlmSecretProviderId): Promise<void>;
};
```

シークレット保存のルール:

- APIキー本文はレスポンス、ログ、会話履歴、チャットイベント、`localStorage`、ワークスペース内ファイル、`.data`配下のJSONに保存・表示しない。
- APIキー入力値はZodでprovider IDと空文字でない文字列を検証する。
- 保存後のAPIレスポンスはステータスだけを返し、APIキー本文を返さない。
- 環境変数由来のAPIキーはUIから上書き・削除しない。Web開発版と`desktop:dev`では、UIで環境変数で設定済みであることと、アプリ内から変更できないことを表示する。デスクトップ配布版ではLLM APIキー環境変数を参照しないため、`source: "env"`は返さない。
- OSシークレットストア由来のAPIキーはUIから更新・削除できる。
- providerごとの保存名はアプリ固有のservice/account名に固定し、ワークスペースパスやチャット内容を含めない。
- base URLなどAPIキー以外の接続設定はAPIキー本文とは別の非シークレット接続設定として扱う。ただし、認証トークンを含むURLは拒否し、レスポンス、ログ、会話履歴に露出しないようにする。

プロバイダー固有の初期化、APIキー名、base URL、モデル生成方法は、LLMプロバイダープラグイン境界に閉じ込める。アプリケーションコードは特定プロバイダー固有の型や初期化処理へ直接依存しすぎないようにする。

プロバイダー境界の例:

```ts
import type { LanguageModel } from "ai";

export type ModelProvider = {
  getLanguageModel(modelId: string): LanguageModel;
};
```

LLMプロバイダープラグインの最小イメージ:

```ts
type LlmProviderId = "openai" | "deepseek" | "gemini" | "anthropic" | "openai-compatible";

type LlmModelDefinition = {
  id: string;
  displayName: string;
  supportsTools: boolean;
  contextWindowTokens?: number;
};

type LlmProviderPlugin = {
  kind: "llm-provider";
  id: LlmProviderId;
  displayName: string;
  envKey: string;
  connectionSettingsPolicy: "none" | "optional-base-url" | "required-base-url";
  models: LlmModelDefinition[];
  createModel(modelId: string): LanguageModel;
};
```

    - `supportsTools`は接続先サーバーとモデルに依存する。ローカル接続先は既定`false`とし、ユーザーが明示的に有効化できる。OpenRouterなどクラウド接続先のユーザー定義プロフィールは既定でtool対応として扱う。環境変数でローカルモデルを指定する場合は`GHOSTWRITER_OPENAI_COMPATIBLE_TOOL_MODELS`にtool対応モデルIDを列挙できる。

モデルIDは各AI SDK providerに渡す値として扱う。実装時点のproviderが要求する正式なモデルIDと異なる場合は、仕様・タスクを更新して実装と一致させる。

OpenAI、Anthropic、Gemini、DeepSeekの固定モデル候補を更新するときは、`docs/llm-model-catalog-update.md`のAPI事前確認、テスト先行、実装、文書同期、完了確認に従う。ChatGPTプランの動的inventoryと`openai-compatible`の接続先・ユーザー指定モデルは、この固定カタログ更新の対象外とする。

非廃止の既存モデルID（例: `gpt-5.4-mini`、`claude-sonnet-4-6`）は互換のため候補に残す。内蔵プリセットは最新推奨モデルへ更新するが、保存済みプロフィールや用途別割り当ては利用可能な限りそのまま維持する。

DeepSeekの`deepseek-flash`は既定のthinking modeで`temperature`が効かないため送らない。旧`deepseek-v4-flash`は退役済みだが互換ルーティングが有効な間は保存済み設定のため候補に残す。Geminiの`gemini-3.8-flash`、`gemini-3.7-flash`、`gemini-3.6-flash`、`gemini-3.5-flash-lite`とAnthropicの`claude-opus-4-7`以降のモデル（`claude-opus-4-7`、`claude-fable-5`、`claude-fable-5-1`、`claude-opus-4-8`、`claude-sonnet-5`、`claude-opus-5`、`claude-opus-5-5`）はAPIが`temperature`/`top_p`/`top_k`を拒否する。モデル定義の`supportsTemperature: false`を`ResolvedLlmProfile`へ引き継ぎ、実行時は`sampling`パラメータを送らない。他のモデルでは従来どおりプロフィールの`temperature`を使う。

OpenAIのGPT-6系はResponses APIで実行し、reasoning時は`temperature`などのsamplingパラメータを送らない。

`contextWindowTokens`が未定義または不明なモデルでは、コンテキスト使用率表示のfallbackとして`200000` tokensを使う。これはusage上限や出力上限ではなく、使用率計算専用の既定値とする。解決順は、ユーザー定義プロフィールの`contextWindowTokensOverride`、provider/model定義の`contextWindowTokens`、fallback `200000`の順とする。`contextWindowTokensOverride`は`maxOutputTokens`とは別フィールドとして扱う。

既定のprovider/modelは環境変数で指定できる。

```text
GHOSTWRITER_DEFAULT_PROVIDER=deepseek
GHOSTWRITER_DEFAULT_MODEL=deepseek-v4-pro
```

未指定時は`deepseek` / `deepseek-v4-pro`を通常チャット用の優先候補として扱う。ただし、APIキーが未設定で利用できない場合は、利用可能なproviderの内蔵LLMプロフィールプリセットへフォールバックする。

環境変数の正式名は`GHOSTWRITER_*`とする。旧`SIMPLE_AI_AGENT_*`は互換のため読み取りだけ継続し、新旧の両方が設定されている場合は`GHOSTWRITER_*`を優先する。

### LLMプロフィール

LLMプロフィールは、ユーザーが「普段用」「執筆用」「検索用」などの実行設定を名前付きで管理する単位とする。アプリ内のエージェントやサブエージェントは、provider/modelを直接選ぶのではなく、用途ロールからLLMプロフィールを解決して使う。

最小の型イメージ:

```ts
type LlmProfileSource = "built-in" | "user";

type LlmProfileRole = "main" | "writing" | "simple" | "search";

type LlmProfile = {
  id: string;
  source: LlmProfileSource;
  name: string;
  providerId: LlmProviderId;
  modelId: string;
  baseURL?: string;
  supportsToolsOverride?: boolean;
  temperature?: number;
  maxOutputTokens?: number;
};

type LlmRoleAssignments = {
  main: string;
  writing: string;
  simple: string;
  search: string;
};
```

用途ロール:

- `main`: 通常チャット、作業計画、ユーザー意図の整理に使う。
- `writing`: 本文生成、文体調整、推敲、重要な編集案作成など、創作品質が重要な処理に使う。
- `simple`: 軽い要約、分類、短い整形、低リスクな判断に使う。
- `search`: `workspace-search-sub-agent`など、検索語分解、候補収集、検索結果要約に使う。

内蔵LLMプロフィールプリセット:

- `deepseek`
  - `main`: `deepseek-v4-pro`
  - `writing`: `deepseek-v4-pro`
  - `simple`: `deepseek-flash`
  - `search`: `deepseek-flash`
- `openai`
  - `main`: `gpt-6-sol`
  - `writing`: `gpt-6-astra`
  - `simple`: `gpt-6-luna`
  - `search`: `gpt-6-luna`
- `gemini`
  - `main`: `gemini-3.8-flash`
  - `writing`: `gemini-3.8-flash`
  - `simple`: `gemini-3.5-flash-lite`
  - `search`: `gemini-3.5-flash-lite`
- `anthropic`
  - `main`: `claude-opus-5-5`
  - `writing`: `claude-fable-5-1`
  - `simple`: `claude-haiku-4-5-20251001`
  - `search`: `claude-haiku-4-5-20251001`

内蔵プリセットのルール:

- 内蔵プロフィールはアプリ定義として常に存在してよいが、対応するAPIキーが未設定のproviderに属するプロフィールは利用不可として扱う。
- 内蔵プロフィールは削除できない。ユーザーは内蔵プロフィールを複製してユーザー定義プロフィールを作成できてよい。
- ユーザー定義プロフィールは、名前、provider、model、temperature、最大出力トークン数、任意のコンテキスト長上書き（`contextWindowTokensOverride`）を編集できる。
- `maxOutputTokens`を明示しない場合の用途別既定値は、`main`が4096、`writing`が65536、`simple`と`search`が2048とする。ユーザーがプロフィールまたはmodel直接割り当てで明示した値は維持する。
- providerが`openai-compatible`の場合、ユーザー定義プロフィールはbase URLを保存する。base URLは`http://localhost:1234/v1`や`https://openrouter.ai/api/v1`のようなエンドポイントを想定する。
- providerが本家OpenAI、DeepSeek、Gemini、Anthropicの場合、base URLは任意扱いとする。未指定ならproviderの既定値または環境変数を使う。指定できる場合でも、通常のユーザーには前面に出さず詳細設定として扱う。
- ユーザー定義プロフィールの保存時はZodで名前、provider ID、model ID、base URL形式、数値範囲、`supportsToolsOverride`を検証する。
- プロフィールにはAPIキー、ワークスペースパス、チャット本文を保存しない。
- base URLにユーザー名、パスワード、APIキー、クエリ文字列、フラグメントを含めることはできない。

用途別割り当ての初期化とフォールバック:

- 設定済みの用途別割り当てがない場合、サーバーは利用可能providerの内蔵プリセットから`main`、`writing`、`simple`、`search`を初期化する。
- `GHOSTWRITER_DEFAULT_PROVIDER`で指定されたproviderが利用可能な場合は、そのproviderの内蔵プリセットを優先する。
- 指定providerが未設定または利用不可の場合は、アプリ定義順の利用可能providerを使う。アプリ定義順は`deepseek`、`openai`、`gemini`、`anthropic`、`openai-compatible`とする。
- 複数providerを利用できるユーザーは、用途ごとに異なるproviderのプロフィールを割り当てられる。
- 割り当て済みプロフィールが削除、未知、またはAPIキー未設定で利用不可になった場合は、同じ用途ロールの利用可能な内蔵プロフィールへフォールバックする。フォールバック先がない場合は明確なエラーにする。
- ツール実行を伴う用途では、`supportsTools: true`のモデルを持つプロフィールだけを選択可能にする。
- 用途ロールの解決結果はチャットイベントまたは完了メタデータに含め、UIで使用プロフィールを確認できるようにする。

プロバイダー・モデル選択のルール:

- サーバーは登録済みの`LlmProviderPlugin`だけを許可する。
- サーバーは選択されたプロバイダーの`models`に含まれる`modelId`だけを許可する。ただし`openai-compatible`は接続先ごとにモデルIDが変わるため、プロフィール保存時に検証済みのユーザー指定`modelId`も許可する。
- `openai-compatible`のbase URLはプロフィールまたは環境変数で必須とする。その他providerのbase URLは任意で、未指定時はprovider既定値を使う。
- ツール実行を伴うエージェントでは、`supportsTools: true`のモデルを持つプロフィールだけを選択可能にする。
- 未知の`providerId`、未知の`modelId`、必要なAPIキー不足は明確なエラーにする。
- `runAgentLoop`はプロバイダー固有の分岐を持たない。
- DeepSeek、OpenAI、Gemini、Anthropic固有の設定は、それぞれのLLMプロバイダープラグインに閉じ込める。
- 会話履歴には必要に応じて使用したプロフィールID、プロフィール名、`providerId`、`modelId`、用途ロールを保存してよいが、APIキーやbase URLなどのシークレットは保存しない。

チャットAPIは、任意の通常チャット用プロフィール選択を受け取れるようにする。

```ts
type ChatLlmProfileSelection = {
  llmProfileId: string;
};
```

`llmProfileId`が省略された場合は、サーバー側の用途別割り当てで`main`に設定されたプロフィールを使う。UIからの切り替えは、サーバーが返す利用可能プロフィール一覧を使って行う。APIキーの入力・保存・削除は設定ページから行い、APIキー本文の表示・再取得は行わない。

エージェント実行はVercel AI SDKの型に合わせる。

- メッセージ表現はAI SDKの`CoreMessage`またはUI連携に適した`UIMessage`を基準にする。
- サーバー側の生成処理は原則として`streamText`を使う。
- ツール定義は`tool({ description, inputSchema, execute })`形式にする。
- 複数ステップのツール実行が必要な場合は、AI SDKの`stopWhen`やステップ制御を使う。
- UIに送るイベントは`streamText`の`fullStream`から、テキスト差分、ツール呼び出し、ツール結果、完了情報をアプリ用イベントへ変換する。
- 通常APIの`reasoning-delta.text`を表示専用の共通イベントへ変換する。OpenAI providerはSDK middlewareで`reasoningSummary: "auto"`を既定設定とする。raw reasoning通知、暗号化された内容、provider metadataは表示へ転送しない。

### ワークスペース指示ファイル

アクティブワークスペース直下に`AGENTS.md`が存在する場合、サーバー側で読み取り、エージェントのsystem promptへ追加する。

ルール:

- 読み込み対象はワークスペース直下の`AGENTS.md`のみとする。
- サブディレクトリ配下の`AGENTS.md`はMVPでは自動読み込みしない。
- `AGENTS.md`が存在しない場合は追加指示なしで実行する。
- `AGENTS.md`は通常のテキストファイルとしてファイルツリー、エディター、AIツールの対象にできる。
- ユーザーはエディターで`AGENTS.md`を編集・保存できる。
- エージェントは`Read`、`Edit`、`Create`で`AGENTS.md`を扱える。ただし`Edit`と`Create`は他のファイルと同じくユーザー承認制にする。
- `AGENTS.md`の内容はアプリ固定の安全ルール、ワークスペース境界、承認制編集、APIキー秘匿、ツール制約を緩和できない。
- system promptの合成では、アプリ固定の安全・操作ルールを`AGENTS.md`より優先する。
- `AGENTS.md`はテキストとして安全に読める場合だけsystem promptへ追加する。NULLバイトを含む、読み取り不能、またはサイズ上限を超える場合は追加しない。
- `AGENTS.md`のsystem prompt読み込み上限は既定で64KiBとする。環境変数で変更できるようにしてよい。
- `AGENTS.md`の読み込み失敗はチャット実行全体の致命エラーにしない。必要に応じてUIイベントまたはログで理由を確認できるようにする。
- 会話履歴には`AGENTS.md`本文を毎回保存しない。必要な場合は、読み込み有無、ハッシュ、読み込み時刻などの軽量なメタデータに留める。

system promptの優先順:

1. アプリ固定の安全・操作ルール
2. `AgentProfile`の基本system prompt
3. 有効化済み`AgentSkill`の追加指示
4. ワークスペース直下`AGENTS.md`の追加指示
5. ユーザーのチャット入力

### 章コンテキスト参考ファイル

章の概要、章内プロット、執筆メモは、ユーザーとAIが共有する通常のワークスペースファイルとして扱う。

目的:

- AIが本文の執筆、推敲、整理を行うとき、現在の章に関係する概要やメモを優先して参照できるようにする。
- ユーザーがAIの参照元を確認し、古い設定や没メモを自分で修正できるようにする。
- AI専用の不可視コンテキストを増やさず、ワークスペース内の資料を明示的に管理できるようにする。

ルール:

- 章コンテキスト参考ファイルはファイルツリーに表示し、エディターで開いて編集できる通常ファイルとする。
- 章コンテキスト参考ファイルをアプリ内部の隠しデータ、検索インデックス、またはAIだけが読める専用ファイルとして扱わない。
- `小説/第001章/本文.txt`のような本文ファイルを対象にAIチャットを実行する場合、同じ章ディレクトリ内の`章内プロット.md`、`概要.md`、`メモ.md`、`登場人物.md`を優先的な参考候補として扱う。
- 章ディレクトリ外の共通資料として、`プロット/`、`設定/`、`資料/`、`メモ/`配下のテキストファイルを検索対象にできる。
- これらのファイルは自動でsystem promptへ全文投入しない。エージェントは必要に応じて`Glob`、`Search`、`Grep`、`Read`で探索・参照する。
- `AGENTS.md`は守るべき追加指示として扱い、章コンテキスト参考ファイルは創作上の参考資料として扱う。参考資料の内容はアプリ固定の安全ルール、ワークスペース境界、承認制編集、APIキー秘匿、ツール制約を緩和できない。
- AIが章コンテキスト参考ファイルを参照した場合、チャットペインのツール実行状況または応答内で参照したワークスペース相対パスを確認できるようにする。

### 章完了時の概要更新支援

章を書き終わった後、ユーザーが明示的に依頼した場合に、AIが本文を読み取って章の概要や章内プロットの更新案を作成できるようにする。

目的:

- 書き終えた本文の実態を、次章以降で参照する概要や章内プロットへ反映しやすくする。
- 執筆中の途中状態や没展開を自動で概要へ混ぜないようにする。
- 章概要の更新をAI編集承認フローに乗せ、ユーザーがdiffを確認してから反映できるようにする。

ルール:

- 概要更新は本文保存時や一定文字数到達時に自動実行しない。
- ユーザーのチャット依頼、または将来追加する章完了操作など、ユーザーの明示操作をきっかけにする。
- AIは対象章の本文を読み、同じ章ディレクトリ内の`概要.md`または`章内プロット.md`への編集案を作成できる。
- 対象の概要ファイルが存在しない場合、AIは`Create`で新規作成案を作成してよい。ただしApplyは他のファイル作成と同じくユーザー承認制にする。
- 対象の概要ファイルが存在する場合、AIは`Edit`で既存内容を置き換えまたは追記する編集案を作成する。即時にディスクへ書き込まない。
- 概要更新案は、本文で実際に起きた出来事、登場人物の状態変化、未解決の伏線、次章へ持ち越す情報を中心にまとめる。
- `AGENTS.md`や共通資料の指示と矛盾しない範囲で更新案を作成するが、概要更新によってアプリ固定の安全ルール、ワークスペース境界、承認制編集、APIキー秘匿、ツール制約を緩和できない。

### エージェントループ設計

`vercel-ai`実行方式のエージェントループは、メインエージェントと将来追加するサブエージェントで共通化する。

メインエージェント専用の実装にせず、共通の`runAgentLoop`にエージェントプロファイルを渡して振る舞いを切り替える。

プロファイルの例:

```ts
type AgentProfile = {
  id: string;
  name: string;
  systemPrompt: string;
  llmProfileRole?: LlmProfileRole;
  temperature?: number;
  maxOutputTokens?: number;
  stopWhen?: unknown;
  activeTools?: Array<
    | "Read"
    | "Edit"
    | "Create"
    | "CreateDirectory"
    | "Glob"
    | "Grep"
    | "Search"
    | "UpdatePlan"
    | "DelegateWriting"
    | "CreateWritingEditProposal"
    | "SpawnSubAgent"
    | "ListSkills"
    | "UseSkill"
  >;
};
```

差分は以下の設定で表現する。

- system prompt
- 利用可能ツール
- LLMプロフィール用途ロール
- temperatureなどの生成パラメータ
- 最大ステップ数や停止条件
- UIへ表示するイベント粒度

`vercel-ai`の組み込みmain/chatプロフィールは1リクエスト最大64ステップとする。ファイル保存ではステップ数をリセットしない。ツール呼び出しを最後に停止条件へ達した場合は、会話に`step_limit`警告を保存し、処理回数の上限と「続けて」による継続依頼を案内する。自動で無制限に再実行しない。read-only/searchサブエージェントは最大4ステップとする。

SDKの`fullStream`の`error`はアプリケーションの失敗処理へ伝播し、`tool-error`は本文や生のエラー情報を含めない失敗tool resultへ変換する。致命的なストリームエラー時は途中までの回答・完了済み編集案を残し、実行中toolの完了を確認できないことを表示・保存する。失敗処理では未適用の編集案を新たにApplyしない。既に自動Applyされたファイルと取り消し情報は維持する。

`DelegateWriting`のproduction生成はAI SDKの`streamObject`を使う。部分objectの`content`（新規）または`newText`（編集）の受信文字数を、toolCallIdに紐づく進捗observerからツール実行表示へ通知する。`oldText`・JSON記法・推論は文字数に含めない。最初の本文受信を通知し、その後の更新は最短250ms間隔に抑える。本文未受信時は応答待ちと表示し、完了予定・進捗率を推測しない。ツール履歴を折りたたんでいても進捗を表示し、完了・失敗で消去する。部分本文をHTTPイベント、通常履歴、main model入力、ファイルへ送らない。正常終了と最終schema検証が済んだobjectだけを成果物へ変換する。出力上限、ストリームエラー、finish欠落では成果物を発行せず、通常のtool失敗経路へ返す。

MVPではメインエージェントから`SpawnSubAgent`でサブエージェントを起動できる最小基盤を持つ。サブエージェントプロファイルは、汎用調査用の`read-only-sub-agent`と、ワークスペース内検索に特化した`workspace-search-sub-agent`を持つ。どちらも利用可能ツールは`Read`、`Glob`、`Grep`、`Search`に限定する。`workspace-search-sub-agent`は`search`用途ロール、軽い整理や要約を目的にしたサブエージェントは`simple`用途ロールを使う。

本文の続き・書き直し・推敲や新規シーン作成など、原稿へのprose生成は`SpawnSubAgent`ではなくメインエージェント専用の`DelegateWriting`経路で`writing`用途ロールへ委譲する。既存ファイルでは対象を`Read`した後に`DelegateWriting`を呼び、存在しない新規ファイルでは`Read`なしでcreate modeの`DelegateWriting`を呼ぶ。返却されたopaque `artifactId`だけを`CreateWritingEditProposal`へ渡し、既存ファイルは承認制Edit proposal、新規ファイルは承認制Create proposalとして提示する。`DelegateWriting`成功結果に原稿本文を含めず、registryは`runAgentLoop`の1回の実行だけが所有する。展開相談、workspace検索、Readのみで答えられる質問、chat-only例文、通常会話では`DelegateWriting`を使わない。対象ファイルが不明確な場合は委譲せずユーザーへ確認する。`writing` profileが利用不能な場合、main modelへ黙ってfallbackしない。同一runで`DelegateWriting`が失敗した`targetPath`へgeneric `Edit`またはgeneric `Create`でfallbackすることも拒否する。

- エージェント実行関数にメインエージェント固有の分岐を埋め込まない。
- system promptをコード内に直書きで散らさない。
- ツールセットはサーバー側固定のプロファイルから選択できるようにする。
- `runAgentLoop`は`AgentProfile.llmProfileRole`から用途別割り当てを解決し、該当LLMプロフィールのprovider/modelを使う。`llmProfileRole`が未指定の場合は`main`を使う。
- 個別エージェントプロファイルにprovider/modelを直書きしない。モデル差分はLLMプロフィールと用途別割り当てで表現する。
- `AgentProfile.activeTools`は、そのエージェントに許可するtool名のリストとして扱う。AI SDKへ渡す`tools`は、この許可リストで物理的に絞り込んだものだけにし、未許可toolは`activeTools`だけでなく`tools`本体にも含めない。
- プロファイルが存在しないtool名を参照している場合は、黙って無視せずエラーにする。
- クライアント、チャット入力、ワークスペース直下`AGENTS.md`は、任意のsystem promptやtool権限を追加・上書きできない。
- サブエージェントが使えるツールはサーバー側で固定し、クライアント入力やワークスペース指示で拡張しない。
- サブエージェントには`SpawnSubAgent`を渡さず、ネストしたサブエージェント起動を禁止する。
- サブエージェント実行には1回のメインエージェント実行あたりの起動回数やステップ数などの制限を設け、無制限なspawnや過剰な実行を防ぐ。
- サブエージェントもユーザー承認なしにファイルを書き換えてはならない。サブエージェントプロファイルでは編集案作成ツール、ファイル作成ツール、ディレクトリ作成ツール、plan更新ツール、Apply操作、ネストした`SpawnSubAgent`を持たない。
- 会話履歴には、必要に応じてどのエージェントが生成したメッセージかを記録できる余地を残す。

`workspace-search-sub-agent`は、検索語の分解、`Glob`、`Grep`、`Search`による候補収集、必要最小限の`Read`による確認、検索結果の要約を担当する。`Grep`と`Search`は最大10件、`Read`は最大2000行の既存制限を維持する。出力はメインエージェントが扱いやすいように、根拠ファイルと該当箇所、要約、次に読むべき候補を含む構造化されたテキストにする。メインエージェントと別のエージェントループを持たず、同じ`runAgentLoop`に検索用の`AgentProfile`を渡して実行する。

### AgentSkill

エージェントが必要に応じて作業手順や専門的な振る舞いを読み込めるように、信頼済みローカル定義の`AgentSkill`を扱う。

Skillは任意コード実行やtool権限追加ではなく、system promptへ合成する追加指示として扱う。エージェントは`ListSkills`と`UseSkill`ツールを使い、作業中に必要だと判断したSkillだけを有効化する。専用LLM routerを毎回呼ぶ方式はMVPでは採用しない。

最小の型イメージ:

```ts
type AgentSkill = {
  id: string;
  displayName: string;
  description: string;
  instruction: string;
  triggerHints?: string[];
  requiredTools?: string[];
};
```

Skillのルール:

- Skill定義はサーバー側の信頼済み設定境界に置く。組み込みSkillと、ローカルプロジェクト内の信頼済み`AgentSkillPlugin`から明示的に渡されたSkillを扱う。クライアント入力、チャット履歴、ワークスペース直下`AGENTS.md`から任意のSkill定義を注入できない。
- ワークスペース内の`.skills/`や外部パッケージからのSkill自動探索は対象外とする。
- `ListSkills`は利用可能なSkillの`id`、`displayName`、`description`、必要に応じて短い`triggerHints`だけを返す。`instruction`全文は返さない。
- `UseSkill`は`skillId`をZodで検証し、Skill registryに存在する組み込みSkillまたはplugin Skillだけを有効化する。
- `UseSkill`実行後、同じチャットリクエスト内の次のAI SDKステップから、有効化済みSkillの`instruction`をsystem promptへ合成する。
- `UseSkill`はSkillの有効化イベントをtool結果として返すが、Skill本文全文をチャット履歴へ保存しない。会話履歴には必要に応じて`skillId`、有効化時刻、表示名などの軽量メタデータだけを保存する。
- 同じSkillが複数回指定された場合は重複してsystem promptへ追加しない。
- Skillの`requiredTools`は権限拡張には使わない。`AgentProfile.activeTools`で既に許可され、実際に登録済みのtoolだけがAI SDKへ渡される。
- Skillの内容はアプリ固定の安全ルール、ワークスペース境界、承認制編集、APIキー秘匿、tool権限、サブエージェント制限を緩和できない。
- サブエージェントにSkill利用を許可するかは`AgentProfile.activeTools`で制御する。MVPではメインエージェントにだけ`ListSkills`と`UseSkill`を渡す。
- Skillが有効化されたことはチャットペインのツール実行状況で簡潔に表示できる。

## AIツール

エージェントは以下のツールを使用できる。

```ts
Read(path: string)
Edit(path: string, oldText: string, newText: string)
Create(path: string, content: string)
CreateDirectory(path: string)
ReadDroppedTextFile(droppedFileId: string)
PlaceDroppedTextFile(droppedFileId: string, targetPath: string)
Glob(pattern: string)
Grep(query: string, options?: GrepOptions)
Search(query: string)
UpdatePlan(items: PlanItem[])
DelegateWriting(targetPath: string, instruction: string)
CreateWritingEditProposal(artifactId: string)
SpawnSubAgent(profileId: string, purpose: string, prompt: string)
ListSkills()
UseSkill(skillId: string)
```

これらはアプリ組み込みのコアツールとして扱う。コアツールはMVPの基本機能であり、外部プラグインによって上書きまたは置き換えられてはならない。

`Edit`、`Create`、`CreateDirectory`の承認要否は実行種別で決定する。AIアシストの編集提案は承認制とし、チャットモードでは「モード構成」の定義に従いconflict確認後に自動適用する。パス検証などの安全ルールは実行種別に関係なく適用する。

`ReadDroppedTextFile`と`PlaceDroppedTextFile`は、現在の`vercel-ai`チャット要求でstageされたopaque IDだけを受け付けるrequest-scoped toolとする。前者は検証済み本文を読み、後者は一時ファイルの元byte列と一致する本文からCreate proposalを作成し、安全なworkspace相対pathへ自動適用する。別workspace、別会話、別request、期限切れ、既に消費済みのIDは拒否する。

ツールの入力・出力スキーマはZodで定義する。

実装ではVercel AI SDKの`tool`ヘルパーを使い、各ツールの`inputSchema`にZodスキーマを渡す。ツール本体のローカルファイル操作は既存のサービス層へ委譲し、AI SDKの`execute`内にファイルシステム処理を直接書き込みすぎない。

`UpdatePlan`は現在のチャットリクエスト中の作業順序を表示するための表示専用ツールとする。ファイル読み書き、編集案Apply、承認操作は行わず、チャットペインのplan状態だけを更新する。

plan itemは`id`、`title`、`status`、任意の`detail`を持つ。`status`は`pending` / `in_progress` / `completed` / `blocked` / `skipped`のいずれかとし、`in_progress`は同時に最大1件とする。

planはチャットリクエスト単位の実行状態として初期化し、新しいチャット送信へ前回の実行中planを引き継がない。会話履歴にplan表示データを保存する場合でも、再読み込み後の過去planは履歴表示として扱い、次回リクエストの実行中状態として復元しない。

`SpawnSubAgent`はメインエージェント専用の委譲ツールとする。入力はZodで検証し、`profileId`はサーバーが許可したサブエージェントプロファイルだけを受け付ける。実行結果はメインエージェントへ構造化して返し、エラーもチャット応答で扱える形にする。

`DelegateWriting`はメインエージェント専用の本文生成委譲ツールとする。入力はZodで`{ targetPath: string, instruction: string }`を検証する。server側で正規化済み`targetPath`の状態を判定し、対象ファイルが存在しない場合だけcreate modeのwriting委譲を許可する。create modeでは同一run内の`Read`は不要とする。対象ファイルが既に存在する場合は、同一run内で`Read`済みであることを実装側で保証し、未読の場合は構造化エラーを返す。ディレクトリ、バイナリ、読み取り上限超過、親ディレクトリ不存在など存在するが新規ファイルとして扱えない対象はcreate modeにしない。`resolveLlmProfileForRole("writing")`で解決したprovider/modelへAI SDK structured generationを行い、run-scoped registryへ`artifactId`、`targetPath`、`operation: "edit" | "create"`、`oldText`、`newText`、writing role/provider/model metadataを保存する。create modeではregistryの`oldText`は常に空文字とし、`newText`に生成本文だけを保持する。成功時のpublic tool resultは`status`、`artifactId`、`targetPath`、`operation`、`latencyMs`、writing側`tokenUsage`（`llmProfileRole: "writing"`、`providerId`、`modelId`必須）だけを返し、原稿本文は含めない。失敗時は`{ message, status: "error", targetPath }`を返し、`artifactId`は発行しない。`artifactId`は`crypto.randomUUID`などのopaque IDとし、text/pathから導出しない。registryはsub-agentや別runと共有しない。

`CreateWritingEditProposal`はメインエージェント専用のwriting proposal作成ツールとする。入力はZod strict schemaで`{ artifactId: string }`だけを受け付け、`path`/`oldText`/`newText`/`content`/`operation`は受理しない。server側でregistry entryを解決し、registryの`operation`に基づいて既存の承認制`createEditProposal`または`createFileProposal` serviceへ委譲する。proposalへ必ず`sourceRole: "writing"`を付与し、Applyはしない。`artifactId`はsingle-useとし、proposal作成成功後に消費する。未知、別run、使用済みIDは拒否する。proposal作成が失敗した場合はartifactを消費せず再試行可能とする。

同一runで`DelegateWriting`を試行した`targetPath`が失敗した場合、実装側はそのnormalized pathをrun-scoped Setへ記録し、同一runの残りでそのpathへのgeneric `Edit`とgeneric `Create`を拒否する。無関係なpathへのgeneric `Edit`/`Create`は従来どおり許可する。writing provenanceは`CreateWritingEditProposal`経由でのみ付与し、generic `Edit`/`Create`のtext一致から`sourceRole`を推定しない。LLM自己申告だけで`sourceRole`を設定しない。

`runAgentLoop`の`tool-result` eventと`src/evals/agentHarness.ts`から、`DelegateWriting`/`CreateWritingEditProposal`のtool call/result、`artifactId`、`operation`、`proposal`の`operation`と`sourceRole: "writing"`を観測できる。eval harnessはregistry本文やraw manuscriptを永続化しない。

structured output失敗の調査用に、`runAgentLoop`へoptionalな`onDelegateWritingDiagnostic` observerを注入できる。`writing` profile解決後に構造化生成または直後のlocal schema parseが失敗した場合のみ、1件のsanitized diagnostic（`type: "delegate-writing-error"`）を通知する。成功時、未読エラー、`writing` profile解決失敗時は通知しない。production通常経路はobserverを接続し、sanitized diagnosticだけを固定event名`delegate-writing-diagnostic`付きのserver logへ1件記録する。logging失敗は既存の`DelegateWriting` tool error result `{ message, status: "error", targetPath }`とagent loopへ影響させない。diagnosticは`DelegateWriting` tool result、`AgentLoopEvent`、main model入力、通常の会話履歴へ露出しない。

diagnosticに含めてよいfieldは、失敗分類（`empty_response` / `json_parse_failure` / `schema_validation_failure` / `provider_error` / `post_generate_validation_failure` / `unknown`）、安全化済み`errorMessage`、既知SDK errorの`errorName`/`errorType`、cause chainの既知error名のみ、`finishReason`、集約`tokenUsage`、`llmProfileRole`/`llmProfileId`/`providerId`/`modelId`、`hasRawText`/`rawTextLength`、`NoObjectGeneratedError.response`からの`id`/`modelId`/`timestamp`、cause chain上の`APICallError`からの`statusCode`/`isRetryable`（深さ・循環制限付き）に限定する。`hasRawText`は`NoObjectGeneratedError.text`プロパティが存在する場合に`true`とし、空文字でも`rawTextLength: 0`として扱う。未知errorの`errorName`/`errorType`は固定値（`Error`/`Error`、非Errorは`Unknown`/`Unknown`）とする。含めてはならないfieldは、prompt、instruction、原稿本文、API key、authorization/全headers、`requestBodyValues`、`responseBody`/`body`、raw response全文、`TypeValidationError.value`、`JSONParseError.text`、cause message全文、`usage.raw`、provider metadataである。eval harnessは`src/evals/agentHarness.ts`から`RunAgentLoopOptions`とdiagnostic observer/typeをimportして利用できる。

`ListSkills`はメインエージェント専用のSkill一覧ツールとする。返却する内容はSkill選択に必要なメタデータだけに限定し、長いSkill本文を無条件にコンテキストへ投入しない。

`UseSkill`はメインエージェント専用のSkill有効化ツールとする。実行時に`skillId`を検証し、現在のチャットリクエストの実行状態へ有効化済みSkillとして追加する。`runAgentLoop`はAI SDKの次ステップ以降で有効化済みSkillの指示をsystem promptへ合成する。`UseSkill`はファイル読み書き、編集案Apply、tool権限追加、任意コード実行を行わない。

### AgentToolPlugin

将来、組み込みコアツールとは別に、信頼済みローカルコードとしてAIツールを追加できるようにする。

このプラグイン種別は`AgentToolPlugin`と呼び、最初に対応する`kind`は`"agent-tool"`のみとする。将来、別種のプラグインとしてエージェントプロファイルやスキルを追加する可能性があるため、汎用の`Plugin`ではなくツール追加専用の名前を使う。

最小の型イメージ:

```ts
import type { ToolSet } from "ai";

type AgentToolPlugin = {
  kind: "agent-tool";
  id: string;
  displayName: string;
  createTools(context: AgentToolPluginContext): ToolSet;
};
```

`AgentToolPlugin`のルール:

- プラグインはAI SDKの`ToolSet`を返す。
- プラグインが提供する各ツールは、AI SDKの`tool({ description, inputSchema, execute })`形式で定義する。
- ツールの使い方、実行条件、読み取り専用か変更案を作るかなどの説明は、原則として各ツールの`description`に書く。
- プラグイン単位のsystem prompt追加はMVPでは必須にしない。
- プラグインツール名がコアツール名と衝突する場合はエラーにする。
- 複数プラグイン間でツール名が衝突する場合もエラーにする。
- プラグインは信頼済みローカルコードとして扱う。任意コード実行を完全に隔離する仕組みはMVP範囲外とする。
- ただし、プラグインがワークスペース操作を行う場合は、可能な限り既存の安全なサービス層を使う。
- コアの安全ルール、ワークスペース境界、AI編集承認制、APIキー秘匿は、プラグインによって緩和できない。

`AgentToolPluginContext`には、プラグインに渡してよい実行コンテキストだけを含める。

想定する内容:

```ts
type AgentToolPluginContext = {
  workspaceRoot: string;
  services: {
    readWorkspaceFile: unknown;
    globWorkspace: unknown;
    grepWorkspace: unknown;
    searchWorkspace: unknown;
    createEditProposal: unknown;
    createFileProposal: unknown;
    createDirectoryProposal: unknown;
  };
};
```

実装では、`createAgentTools`が以下を合成する。

```text
createAgentTools
  -> createCoreAgentTools
  -> enabled AgentToolPlugin の createTools
  -> ツール名衝突チェック
  -> core tools と plugin tools をマージ
```

`AgentProfile.activeTools`は、コアツールだけでなく有効な`AgentToolPlugin`が提供するツール名も扱えるようにする。存在しないツール名が指定された場合は、黙って無視せず、開発時に原因が分かるエラーとして扱う。

### AgentSkillPlugin

組み込みSkillとは別に、ローカルプロジェクト内の信頼済みpluginから`AgentSkill`を追加できるようにする。

このプラグイン種別は`AgentSkillPlugin`と呼び、Skill定義だけを追加する。`AgentSkillPlugin`はAI toolを登録せず、任意コード実行やtool権限追加の仕組みとして扱わない。

最小の型イメージ:

```ts
type AgentSkillPlugin = {
  kind: "agent-skill";
  id: string;
  displayName: string;
  createSkills(context: AgentSkillPluginContext): AgentSkill[];
};
```

`AgentSkillPlugin`のルール:

- pluginはローカルプロジェクト内の信頼済みコードとして扱う。外部パッケージやワークスペース内任意ファイルからの自動探索はMVP範囲外とする。
- pluginが返すSkillは、組み込みSkillと同じ`AgentSkill`検証を通す。
- Skill IDは全Skillで一意にする。組み込みSkillとplugin Skill、または複数plugin間でIDが衝突した場合はエラーにする。
- `ListSkills`は組み込みSkillと有効な`AgentSkillPlugin`由来のSkillを同じ一覧として扱う。
- `UseSkill`は組み込みSkillとplugin Skillを同じ検証経路で有効化する。
- plugin Skillの`instruction`もsystem promptへ合成する追加指示であり、安全ルール、ワークスペース境界、承認制編集、APIキー秘匿、tool権限、サブエージェント制限を緩和できない。
- plugin Skillの`requiredTools`は権限拡張には使わない。実際にAI SDKへ渡すtoolは`AgentProfile.activeTools`で許可されたものだけにする。
- `AgentSkillPluginContext`には、Skill作成に必要な最小限の設定だけを渡す。ファイル読み書きや外部通信のサービスは原則として渡さない。
- plugin由来Skillであることは、デバッグやUI表示のために`pluginId`などのメタデータとして保持してよい。ただしSkill本文全文を会話履歴へ保存しない。

想定する内容:

```ts
type AgentSkillPluginContext = {
  workspaceRoot: string;
};
```

実装では、Skill registryが以下を合成する。

```text
createAgentSkillRegistry
  -> built-in AgentSkill definitions
  -> enabled AgentSkillPlugin の createSkills
  -> Skill ID 衝突チェック
  -> ListSkills / UseSkill が参照するSkill registryを作成
```

production runtimeでは、信頼済みextension catalogが`AgentSkillPlugin`と`AgentToolPlugin`を別配列で保持する。catalogはproduction API compositionからagent chat handlerを経由して`runAgentLoop`へ明示的に渡す。plugin IDはSkill/Tool pluginを横断して一意とし、pluginの`kind`、非空の`id`と`displayName`、対応するfactory関数をcomposition時に検証する。既定catalogは空とし、拡張を設定しない既存動作を維持する。

catalogは組み込み`AgentProfile` IDごとの`profileToolGrants`も保持する。Tool pluginをcatalogへ登録しただけではplugin toolを有効化せず、`runAgentLoop`が現在のprofile IDに対するtool名の明示grantだけをeffective profileの`activeTools`へ追加する。同じcatalogをrecursive sub-agent runにも渡し、各sub-agentにも自身のprofile IDのgrantだけを適用する。クライアント入力、チャット履歴、ワークスペース直下`AGENTS.md`、Skillの`requiredTools`からgrantを追加または上書きできない。plugin tool定義とtool名衝突はworkspace contextを構築したagent runの開始前に検証し、profile選択後は`selectProfileTools`で許可済みtoolだけをAI SDKへ渡す。

### Read

アクティブなワークスペース内のテキストファイルを読む。

ルール:

- パスはワークスペース配下に解決されなければならない。
- バイナリに見えるファイルは拒否する。
- 大きいファイルは明示的な切り詰めマーカー付きで一部だけ返してよい。

### Edit

編集案を作成する。即時にディスクへ書き込まない。

MVPでの編集動作:

- 完全一致のテキスト置換を行う。
- `oldText`が曖昧でないことを確認する。原則として完全一致が1箇所だけの場合に成功する。
- 互換性のためサーバー側でdiffプレビュー文字列を生成して保存する。チャットUIでは`oldText`/`newText`から表示用diffを再計算し、保存済みdiff文字列のヘッダ行には依存しない。
- ファイルへの書き込み前にユーザー承認を必須にする。
- 1回のAI応答で複数の編集案を作成してよい。
- 複数の編集案がある場合も、Applyは1件ずつ行う。
- ワークスペース相対パスのいずれかのセグメントが`.`から始まるファイルは編集案作成またはApply時に拒否する。

Apply時の動作:

- 現在のファイルを再読み込みする。
- `oldText`が想定どおり一致することを確認する。
- 確認後にのみ書き込む。
- 編集案作成後にファイルが変更されていた場合は`conflicted`として返す。
- 対象ファイルがエディターで未保存状態の場合はApply不可にし、先に保存または変更破棄を求める。

### Create

新規ファイル作成案を作成する。即時にディスクへ書き込まない。

MVPでの作成動作:

- `path`と`content`を受け取り、対象パスの新規ファイル作成案を作成する。
- 対象ファイルが既に存在する場合は作成案を拒否する。
- 互換性のためdiffプレビュー文字列は`/dev/null`から対象ファイルへの追加として生成して保存する。チャットUIでは`oldText`/`newText`から表示用diffを再計算し、追加内容を追加表示として描画する。
- ファイルへの書き込み前にユーザー承認を必須にする。
- 1回のAI応答で複数の作成案を作成してよい。
- 複数の作成案がある場合も、Applyは1件ずつ行う。
- ワークスペース相対パスのいずれかのセグメントが`.`から始まるファイルは作成案作成またはApply時に拒否する。

Apply時の動作:

- 対象ファイルがまだ存在しないことを再確認する。
- 確認後にのみ書き込む。
- 作成案作成後に対象ファイルが作成されていた場合は`conflicted`として返す。
- 対象ファイルがエディターで未保存状態の場合はApply不可にし、先に保存または変更破棄を求める。

### CreateDirectory

新規ディレクトリ作成案を作成する。即時にディスクへ書き込まない。

MVPでの作成動作:

- `path`を受け取り、対象パスの新規ディレクトリ作成案を作成する。
- ファイル作成の`Create`とは別ツールとして扱い、`content`は受け取らない。
- 対象パスにファイルまたはディレクトリが既に存在する場合は作成案を拒否する。
- 親ディレクトリが存在しない場合、MVPでは中間ディレクトリを暗黙に作らず作成案を拒否する。
- プレビューはdiffではなく、作成予定ディレクトリのワークスペース相対パスを表示する。
- ディレクトリ作成前にユーザー承認を必須にする。
- 1回のAI応答で複数のディレクトリ作成案を作成してよい。
- 複数の作成案がある場合も、Applyは1件ずつ行う。
- ワークスペース相対パスのいずれかのセグメントが`.`から始まるディレクトリは作成案作成またはApply時に拒否する。

Apply時の動作:

- 対象パスにファイルまたはディレクトリがまだ存在しないことを再確認する。
- 親ディレクトリが存在することを再確認する。
- 確認後にのみディレクトリを作成する。
- 作成案作成後に対象パスが作成されていた場合は`conflicted`として返す。
- 作成成功後、ファイルツリーを最新状態へ更新する。

### Glob

ワークスペース内のファイルとディレクトリのパス一覧を返す。

`Glob *`のような広い探索では、ファイルだけでなく空ディレクトリも確認できること。AIが保存先候補や既存ディレクトリ構成を把握するために使う。

想定実装:

- ファイル一覧は検索ストア境界のローカル実装で、可能な限り`ripgrep`の`rg --files`を使う。
- ディレクトリ一覧はNode.jsのファイルシステムAPIなどで補完してよい。
- glob条件は`rg`のオプションまたはサーバー側のフィルタリングで適用する。
- ワークスペース相対パスを返す。
- 返却件数は`Grep`や`Search`と同じく最大10件までとする。
- ファイルとディレクトリの両方を含めて安定した順序で返す。

### Grep

検索ストア境界のローカル実装として、`ripgrep`を使ってファイル本文を検索する。

想定実装:

- `rg`を使う。
- パス、行番号、該当行を返す。
- UIとモデルコンテキストを守るため、結果件数は最大10件にする。

### Search

自然文に近い検索要求を扱う高レベルなローカル検索ヘルパー。

MVP実装では以下を許容する。

- クエリから有用な検索トークンを抽出する。
- 1回以上の`rg`検索を実行する。
- 最大10件のランク付けしたパスとスニペットを返す。

実装は検索ストア境界のローカル実装として`ripgrep`を使う。

`Search`は`Grep`より高レベルな検索として扱う。自然文クエリから検索語を作り、複数の`rg`検索を組み合わせて候補を返す。

## 編集承認フロー

```text
ユーザー入力
  -> エージェントがEditを呼ぶ
  -> またはエージェントがCreateを呼ぶ
  -> またはエージェントがCreateDirectoryを呼ぶ
  -> サーバーが編集案または作成案を作成する
  -> チャットUIがdiffプレビューまたはディレクトリ作成プレビューを表示する
  -> ユーザーがApplyまたはRejectを選ぶ
  -> Apply時はconflict確認後にのみディスクへ書き込む
  -> エディターとファイル状態を更新する
```

Rejectされた編集案または作成案も、Reject済みの提案として会話履歴に残す。

チャットモードから送信したチャットでは、上記フローのApply/Reject選択を省略し、conflict確認後に自動でディスクへ書き込む。自動適用された提案は適用済みカードとして会話内へ表示し、取り消し操作で適用前の内容へ復元できる。詳細は「モード構成」のチャットモード定義に従う。AIアシストから作成した編集提案は会話履歴へ保存せず、従来どおり承認制とする。

## 会話履歴

会話履歴はJSONで保存する。

ワークスペースごとに複数会話を作成できるようにする。チャットモードでアクティブワークスペースを開いたときは、最新の会話を自動復元する。ユーザーは新しい会話を作成し、既存会話へ切り替えられる。エディットモードのAIアシストは会話履歴を読み書きしない。

会話履歴ダイアログでは、会話タイトルを含む確認後に任意の会話を削除できる。対象会話のAI応答、圧縮、保存済み旧ターン状態などが実行中なら削除を無効にする。非アクティブ会話削除では現在の会話を維持し、アクティブ会話削除では残存する最新会話へ切り替え、最後の会話なら未選択状態へ戻す。外部CLIのthread操作は行わない。

ツール履歴の折りたたみ状態は会話履歴JSONへ保存しない。過去の会話を再読み込みしたとき、assistantターンごとのツール履歴サマリーは既定で折りたたんだ状態として表示する。

### 会話保存の競合・中断と復旧

- 会話単位のread-modify-write、読み取り、削除は共通の保存窓口を通す。同一プロセスでは正規化した履歴パス単位で直列化し、別プロセスとは同じパスの`.json.lock`ディレクトリで排他する。ロック取得は約2秒まで待ち、取得できない操作はエラーとする。成功した更新を後続更新で取りこぼさず、削除済み会話への更新は失敗させる。一覧全体や1ターンの全結果を単一トランザクションにはしない。
- JSONは同じディレクトリに排他的に作成した一時ファイルへ書き、ファイルのsyncとclose後にrenameで置換する。macOS/Windowsとも既存JSONを先に削除するfallbackは使わない。書き込み・置換失敗時は旧JSONを保持し、一時ファイルを清掃する。異常終了で残った一時ファイルは次の排他取得時に清掃する。
- チャットの自動Applyは原稿変更前にpending proposalを保存する。Apply/Undoは変更前後の全文snapshotと予定するproposal状態を会話JSONの`editRecovery`へ先に保存し、その成功後に原稿を変更し、最後に完了状態を保存する。最後の保存に失敗しても復旧記録は残る。ツール結果には保存済みproposalのIDを`persistedProposalId`で引き継ぎ、ターン終了時には重複追加せずassistantとの関連を補う。過去のtoolCallIdをproposal IDとする履歴も引き続き読み込める。
- 次の会話読み取り・更新時、復旧記録をZodと会話内proposalとの対応で検証し、現在の原稿が予定した変更後全文と一致すればApply済み、Undo後全文と一致すればUndo済みへ復旧する。新規ファイルのUndoは対象の不存在を確認する。復旧処理から原稿への書き込み・削除は行わない。
- 不一致、読み取り不可、不正パス、ディレクトリ操作のように所有者・完了状況が曖昧な場合はsnapshotを保持して`conflicted`とする。原稿変更前に中断した場合も自動再実行せず競合扱いとする。破損した復旧記録は会話の読み込みをエラーにする。同じproposalへのApply/Undo再試行は完了済みの変更を繰り返さず、競合proposalをApplyし直さない。別のproposal IDで新たに依頼した編集は別操作である。
- プロセス強制終了で`.json.lock`が残った場合、ロックを自動で奪わない。Ghostwriter、開発サーバー、関連sidecarをすべて停止したうえで、対象の空の`.json.lock`ディレクトリだけを削除し、アプリを再起動して会話を読み込む。JSONや`editRecovery`を先に消さない。競合時は保持されたsnapshotと現在の原稿を確認して、新しい編集案で続行する。
- 保証対象はこの保存窓口を使うローカルプロセス間の同一会話操作と、Apply/Undoの途中失敗である。別会話や外部エディターとの原稿への同時書き込み、外部からのアプリデータ変更、ネットワークファイルシステム、電源断・OS・ディスク障害全般への耐久性は保証しない。本文が同じ外部置換は識別できない。AIアシストなど会話を持たない別ストアの保存は対象外とする。

初期保存先:

```text
{dataRoot}/
  conversations/
    {workspaceId}/
      {conversationId}.json
  dropped-text-files/
    {workspaceIdHash}/
      {conversationIdHash}/
        {requestId}/
  file-tree-order/
    {workspaceId}.json
  workspace-templates.json
```

`{dataRoot}`の解決順:

1. サーバーruntimeへ明示注入された`dataRoot`
2. 環境変数`GHOSTWRITER_DATA_DIR`（trimmed、相対値はruntime cwd基準で絶対パス化）
3. 互換読み取り用の`SIMPLE_AI_AGENT_DATA_DIR`（trimmed、相対値はruntime cwd基準で絶対パス化）
4. 未設定時の開発用fallback: `{cwd}/.data`

Web開発版では明示注入と対応環境変数がどちらも未設定の場合に4を使う。デスクトップ版sidecarはTauriが取得したOSアプリデータディレクトリを、起動時に絶対パスとして`GHOSTWRITER_DATA_DIR`へ設定する。

`.data`ディレクトリはアプリ管理用とし、既定ではファイルツリーや検索結果に含めない。書き込み不可などstorage利用不能時、APIは内部pathを返さず`Application data storage is unavailable`を返す。

会話データの形:

```ts
type Conversation = {
  id: string;
  workspaceId: string;
  agentRuntime?: "vercel-ai" | "codex-app-server";
  codexThreadId?: string;
  selectedCodexModel?: string | null;
  codexRuntimeMetadata?: {
    model: string;
    modelProvider: string;
    protocolVersion: "v2";
    userAgentOrCliVersion: string;
  };
  title: string;
  lastOpenedAt: string;
  messages: ChatMessage[];
  editProposals: EditProposal[];
  toolActivities: ToolActivity[];
  toolResultSummaries: ToolResultSummary[];
  plans: AgentPlan[];
  createdAt: string;
  updatedAt: string;
};

type ChatMessage = {
  id: string;
  role: "user" | "assistant" | "system" | "tool";
  content: string;
  finishReason?: string;
  tokenUsage?: TokenUsage;
  mainContextSnapshot?: {
    inputTokens: number;
    contextWindowTokens: number;
    providerId: string;
    modelId: string;
    llmProfileRole: "main";
  };
  warnings?: ConversationMessageWarning[];
  createdAt: string;
};

type ToolActivity = {
  id: string;
  assistantMessageId?: string;
  toolCallId: string;
  toolName: string;
  label: string;
  status: "running" | "completed" | "failed";
  detail?: string;
  createdAt: string;
};

type ToolResultSummary = {
  assistantMessageId: string;
  toolCallId: string;
  toolName: string;
  summary: string;
  createdAt: string;
};

type EditProposal = {
  id: string;
  assistantMessageId?: string;
  path: string;
  oldText: string;
  newText: string;
  diff: string;
  operation: "edit" | "create" | "createDirectory";
  sourceRole?: "writing";
  status: "pending" | "applied" | "rejected" | "conflicted";
  title: string;
  createdAt: string;
  updatedAt: string;
};
```

`agentRuntime`は旧履歴の読み取り互換として`codex-app-server`を受理するが、新規作成APIは`vercel-ai`のみ受け付ける。`codexThreadId`、`selectedCodexModel`、`codexRuntimeMetadata`は過去の履歴metadataとして保存互換を維持し、実行には利用しない。

`sourceRole`は`CreateWritingEditProposal`がregistry artifactから作成したproposalにのみ付与する。既存会話履歴の`sourceRole`なしproposalとの互換性を維持するためoptionalとする。

`toolResultSummaries`は、モデル入力へ戻すためのcompact tool result summaryを保持する。各summaryは`assistantMessageId`へ紐づき、raw tool result、ファイル全文、Edit/Create本文やdiffは保存しない。1 resultあたり最大512文字、1 assistant turnあたり最大2048文字、1 conversation全体で最大8192文字までをモデル入力へ戻す。

`toolActivities`はUI表示用であり、モデル入力用summaryとは責務を分ける。

会話履歴からモデル入力を構築する際は`ConversationModelMessageStrategy`を使う。

- `current`: 本文メッセージだけを返し、tool履歴や編集提案を追加しない。
- `compact-tool-results`: 関連するassistant messageの本文末尾へ、boundedな履歴summaryを連結して返す。production agent chatはこのstrategyを使う。

`compact-tool-results`では、過去のtool activity、tool result summary、編集提案の現在statusを固定形式で連結し、これは過去の履歴であり現在のファイル内容を保証しないこと、原稿編集や事実確認ではworkspaceを再度`Read`することを明示する。別assistant messageは増やさない。

- `conversation-compaction`: 最新の会話圧縮checkpoint要約を1件のsystem messageとして先頭に置き、checkpoint以降の`user`/`assistant`/`system`メッセージだけを生の会話として返す。checkpoint以前の通常メッセージはモデル入力へ含めない。`compact-tool-results`と組み合わせ、checkpoint以降のassistant turnにはtool履歴summaryや編集提案状態を連結する。production agent chatはこのstrategyを使う。

会話履歴JSONには`conversationCompactions`配列を保持する。各checkpointは`id`、`createdAt`、`summary`、`sourceMessageIds`、`compactedThroughMessageId`、`compactedThroughCreatedAt`、任意の`tokenUsage`を持つ。既存会話JSONにフィールドがなくても空配列として読み込む。圧縮checkpointは保存済み`messages`を削除せず、モデル入力構築時の履歴戦略としてのみ使う。複数checkpointがある場合、モデル入力へ使うのは最新checkpointだけとする。

圧縮要約はサーバー側のLLM呼び出しで生成し、作品状態・ユーザーの希望・決定事項・未解決の作業・最近の編集・作成を含める。要約は現在のファイル内容を保証しないため、必要に応じて`Read`する注意を含める。作品の状態の正は引き続きワークスペース内ファイルである。

## バリデーションと安全性

- すべてのAPIリクエストをZodで検証する。
- すべてのツール呼び出しをZodで検証する。
- クライアントから渡されたパスを信用しない。
- 共有のワークスペースパスユーティリティを通してパスを解決する。
- パストラバーサルでワークスペース外へ出られないようにする。
- LLM APIキーはサーバー側だけで扱う。
- APIキー本文をクライアントへ返さない。
- 可能な範囲でログからシークレットを除外する。
