# Codex使用枠に余裕がある場合のツリー型multi-agent実装

## When this matters

複数の実装タスクを並行して進められ、Codexの使用枠に余裕があり、調査・設計・レビューに高い推論能力を使いたいとき。

この運用は常用しない。小さな変更、密な往復が必要な変更、同じファイルへ集中する変更では委任コストが上回るため、通常の単独作業を使う。境界が明確な単純実装を委任する場合は、現行ルールに従って`5.6luna`を第一候補にする。

## Field note

メインCodexをオーケストレーターにし、独立した機能タスクごとに子Codexエージェントを割り当てる。子は担当範囲内の小オーケストレーターとして、限定的な調査に加え、子自身が方針、変更範囲、検証方法を確定した明確な実装を孫Codexエージェントへ委任できる。

メインは全体仕様、共有境界、競合解決、最終レビュー、全体検証、タスク完了、commitを担当する。子は担当タスク内の詳細方針、孫への実装指示、孫の差分レビューと差し戻しを担当する。孫へ新しい設計判断や最終統合を任せない。

推奨する役割分担:

```text
メインCodex
├─ 子: 機能タスクA
│  ├─ 孫: Aに必要な限定調査
│  └─ 孫: 子が方針を確定したAの局所実装
├─ 子: 機能タスクB
├─ 子: 機能タスクC
└─ 子: 機能タスクD
   └─ 孫: 子がテストを確定したDの局所実装
```

モデルはタスク全体のラベルだけで決めない。当面は、仕様とテストが確定した局所的なUIや状態遷移を含め、サブエージェントには`5.6luna`を第一候補とする。Lunaでは不足する設計判断、未知要素、影響範囲、回帰リスクが残る担当に限り、必要な能力に応じて`5.6terra`または`5.6sol`を選ぶ。

孫の作業範囲は子より狭く単純になっている前提で、親よりコスト効率のよいモデルを明示的に選ぶ。

| 子のモデル | 孫の基本モデル | 利用できない場合 |
| --- | --- | --- |
| `5.6sol` | `5.6terra`または、明確な単純作業なら`5.6luna` | 孫を作らず子自身で処理する |
| `5.6terra` | `5.6luna` | 孫を作らず子自身で処理する |
| `5.6luna` | 原則としてCodexの孫を作らない | 子自身で処理する |

同じモデルの孫を例外的に使うのは、分離後にも高度な判断が残り、並列化やコンテキスト節約の効果が委任コストを明確に上回る場合だけとする。モデルを切り替えられるよう、孫には親の会話履歴全体を継承せず、必要なファイルと確認事項だけを渡す。

## Reliable procedure

1. メインが必須仕様、対象タスク、Field Guide、関連コードを確認する。
2. タスク間の共有ファイルと共有状態を先に洗い出す。
3. メインがAPI契約と実装方針を決め、可能な限り失敗するテストを先に追加する。
4. 独立性の高い機能タスクごとに子Codexエージェントを作る。変更可能なファイル、対象外、検証方法、報告形式を明示する。
5. 子が孫へ調査を委任する場合は、既存コード探索、影響範囲、実装候補比較などの限定タスクにし、親よりコスト効率のよいモデルと限定コンテキストを明示する。
6. 子が孫へ実装を委任する場合は、子が先に実装方針、変更可能ファイル、対象外、失敗するテストまたは検証方法、期待する報告形式を確定する。
7. 実装担当の孫は指定ファイルだけを変更してtargeted testを実行し、差分の要点、テスト結果、未確認事項を子へ返す。設計変更や共有境界の編集が必要になったら実装を止めて子へ戻す。
8. 子は孫の差分をレビューし、テストと方針に合わなければ同じ孫へ差し戻す。確認後にだけメインへ完了報告する。
9. 同じファイルを複数の子が触る必要がある場合は、server/UI、model/view、調査/実装など責務で分割する。共有ファイルの最終変更はメインが統合する。
10. 子の完了報告だけで完了扱いにせず、メインが重要な根拠、差分、テストを確認する。
11. タスク本文との不一致や不足を見つけたら、メインが新しい失敗テストを追加して同じ子へ差し戻す。
12. メインが共有状態、API router、cleanup、エラー境界、仕様書を統合する。
13. targeted test、型検査、全体test、E2E、build、必要なdesktop test、`git diff --check`をメインが実行する。
14. 完了タスクを`tasks/done/`へ移動し、関連差分をメインがcommitする。

今回有効だった分割:

- チャット添付では、一時保管・AI toolと、クライアント添付UIを別担当にした。
- 会話削除は独立した状態遷移タスクとして分離した。
- Reader選択ジャンプは表示DOMと原文offsetの対応を専任にした。
- Editorとファイルツリーのdropは同じ機能タスクにまとめ、ファイルツリー順序の調査だけを孫へ分けた。
- Playwrightは機能ごとに別ファイルへ分け、共有E2Eファイルの競合を避けた。

## Failure signals

- 複数の子が同じcomponentやcontrollerを同時に大幅変更している。
- 子の報告を理解するために、メインが変更箇所を最初からすべて調査し直している。
- 孫へ実装全体を渡し、子とメインのどちらも設計根拠を確認できていない。
- 子が方針やテストを確定する前に、孫が実装ファイルを編集している。
- 孫の実装を子がレビューせず、そのままメインへ完了報告している。
- 孫が親の全会話履歴と同じモデルを暗黙に継承している。
- unit testは通るが、共有状態のclear、route遷移、cleanup、永続化など統合境界が未確認になっている。
- タスク本文とテストの期待が食い違っている。
- 使用枠が少ないのに、小さな作業ごとにCodex子エージェントを増やしている。

## Recheck when

- Codexのmulti-agent機能、同時実行枠、モデル名、使用枠の計算方法が変わったとき。
- `specs/development-workflow.md`または`AGENTS.md`のLuna優先条件、モデル選択、実装開始ゲートが変わったとき。
- 共有worktreeではなく、agentごとのworktreeや自動mergeを使う構成へ変わったとき。
